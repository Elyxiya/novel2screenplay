## 项目标题行

```
Novel2Screenplay · AI 小说转剧本工具（个人项目）
2026.06 – 2026.09 ｜ Next.js 16 + React 19 + TypeScript + Zod 4 + SQLite / PostgreSQL
一言：把几十万字的长篇小说转成结构化 YAML 剧本，再拆成分镜表；全程 LLM 产出 + 可视化精修 + 原文溯源。
```

## 项目描述（五条主条目）

- **LLM 结构化输出的容错解析**：LLM 返回的 JSON 常带 Markdown 围栏、尾随逗号、单引号键名，直接 `JSON.parse` 会失败；更隐蔽的是解析失败时返回的哨兵对象一旦被调用方漏检，重试逻辑就不触发，长篇小说会静默丢光角色卡。实现四层降级解析（直接解析 → 剥离围栏 → 括号配对提取 → 字符清理），并在调用点显式拦截哨兵主动抛错让重试真正生效；把"只有一个内容块且长度超 3000 字"判定为输出被截断，同样触发重试。单场景转换 3 次重试仍失败时不中断任务，输出带错误码和 `confidence 0.1` 的降级场景，失败原因留在产物里可筛出。

- **长文本的上下文管理**：整本小说几十万字装不进上下文，原方案是按比例截断到 3 万 token 后单次分析——截断位置会落在句子中间，且后半本书的角色和地点完全不参与分析。新增两条路径：按章并行抽取实体/摘要/伏笔再归并成全局设定卡（每个实体记录称呼来自哪一章以便回溯），以及整本不截断送大窗口模型再由守卫检查是否越过窗口 90%；三条路径保留，切换由独立决策函数负责，数据不足时不切换默认。场景上下文从"整张角色表塞进去"改为主角卡常驻 + 配角只注入本场景在场名单命中的 + 前 5 章滚动摘要 + 按章节区间筛未闭合伏笔，prompt 体积不再随全书角色数增长。

- **任务状态持久化与断点恢复**：任务状态原先存在内存里、靠 `globalThis` 挂载躲 Next.js 热重载引起的模块重执行，重启即丢、多实例不共享。改为落 SQLite，并保留原来的类和方法签名做兼容壳，几十个调用点无需改动；恢复锁从进程内的 `Set` 换成数据库层单条 `UPDATE` 达成的 CAS（锁为空或已过期才可抢到，以 `changes > 0` 判定），带 10 分钟 TTL 与 TTL/3 心跳续锁，进程崩溃后锁自行过期释放。恢复逻辑从"重跑全量"改为只重跑失败与待处理场景，再按场景号与旧产物对齐合并后重跑合并阶段。期间修复一个集成测试抓到的缺陷：局部重转路径进入时会把任务状态写成"转换中"，而收尾未写回终态，任务会永久卡住。

- **中文文本处理的几处具体问题**：输入是网文，数据比预期脏。编码上先按 UTF-8 严格模式解码、失败回退 GBK，解完检出替换字符就报错让用户重存，而不是把乱码喂给模型；章节识别覆盖 6 类标题写法（含序章、第X节、Chapter N）并按优先级匹配，两条匹配点相隔过近时做重叠去重，全都匹配不上则按约 2000 字回退切分；角色去重先做标点归一化与"短名 ≥2 字且被长名包含"判定、再用编辑距离归一化后小于 0.3 兜底（包含关系必须排在前面，否则"林黛玉"与"林黛"这类差一字的反而判不出）；时间字段限定在 7 个枚举内并配中英表述的映射表，映射不到落 `unknown` 而不原样写入；正文进管线前按规则清噪声行（盗版水印/广告/章尾引导/乱码），每条规则要求两个以上信号（关键词 + 行长，或乱码占比 + 行长）以免误删正文，清洗结果带留痕（移除行数、按规则计数、抽样原文）。

- **可嵌入的 Agent 工作台与消息桥**：工作台需要被嵌进其他页面，但面板若自己发请求就要拿到宿主的会话。把工作台拆成宿主与面板两侧：面板做成 web component（React 挂进 shadow DOM），自身不持有 `fetch`、`EventSource`、Cookie 与路由，只通过 `postMessage` 上报意图（启动任务／人工介入／带建议重生成／导航）；宿主执行真实调用并订阅 SSE，再把 Agent 事件回推给面板渲染。协议消息统一带协议版本与请求关联 ID；入站做两层守卫——origin 白名单加消息结构校验（缺版本号、缺类型、类型不在白名单一律拒绝），伪造 origin 的消息在进入业务逻辑前即被丢弃。配了同页宿主与跨域 iframe 两个 demo，以及覆盖 schema 校验、白名单放行、伪造 origin 拒绝、事件往返的协议单测。

## 压缩版（三条，简历空间紧张时用）

- **LLM 结构化输出的容错解析**：针对 LLM 返回 JSON 不稳定（Markdown 围栏、尾随逗号、单引号键名）与长输出被截断两种情况，实现四层降级解析 + 截断判定 + 3 次重试；并修掉"解析失败返回哨兵对象被漏检、导致重试不触发、长篇静默丢角色卡"的隐患。失败场景降级为带错误码的占位而非中断任务。

- **长文本上下文管理**：整本小说超出上下文窗口，为此实现按章并行抽取再归并成全局设定卡、以及整本不截断的长上下文两条路径（切换由独立决策函数负责，数据不足不切默认）；场景上下文改为主角卡常驻 + 配角按在场名单注入 + 滚动摘要 + 未闭合伏笔按章节区间注入，prompt 体积与全书角色数解耦。

- **任务状态持久化与断点恢复**：任务状态从内存迁至 SQLite（保留原方法签名做兼容壳，调用点零改动）；恢复锁改为数据库层单条 `UPDATE` 达成的 CAS，配 TTL 与心跳续锁；恢复从重跑全量改为只重跑失败场景后重合并。另修复一处状态覆盖缺陷（局部重转收尾未写回终态导致任务永久卡住）。

## 条件条目（默认不启用 · 确认能讲清再放进去）

> **启用前提**：Agent 的工具调用链路目前未接通——LLM 调用选项里没有 `tools` 字段，从内容中解析工具调用的函数从未被调用，因此仓库内的 8 个内置工具在实际编排链路中不会被执行，每个阶段实际是一次 LLM 调用。
> 若你已自行接通并跑通，可用下面这条；否则**不要写**。

- **Agent 运行时与四阶段编排**：实现 Agent 运行时骨架——7 状态状态机（转移表驱动）+ 三层记忆（工作记忆超预算淘汰最旧消息、会话记忆保留最近 20 轮、长期记忆持久化）+ 步数与 token 预算上限 + 事件流；用其把四阶段转换做成一阶段一实例的串行编排，每阶段结束过一道质量门（分数阈值、必查维度、最大问题数、失败动作、最大重试次数均为配置表），门不通过时挂起等人工介入（通过／重试／带建议重做／丢弃），任务持久化后可重启续跑。门判定有明确顺序：身份一致性失败优先否决 → 逐维度比阈值 → 问题数超限 → 总分不达标 → 落入阈值上方 10 分区间判建议人工审核。
