## 二、逐页要点（与 PPT 对应）

**P1 封面**：项目名 + 一句定位 + 周期/角色。开场只说一句："这是一个把小说转成结构化剧本的工程化项目，我重点讲三件事：上下文、可靠性、以及怎么证明它变好了。"

**P2 三个断点**
- 装不下：整本 30 万字，原方案截断 3 万 token，样本里 59% 正文从未参与分析。
- 不可信：LLM 输出可能漏人、编人、把背景写成动作；早期评测用自己那次当金标准，F1 恒为 1.0。
- 改不动：改一次 prompt 全链路重跑，没有局部修复与回放。

**P3 系统与闭环**
- 三条线：创作台（/writer）→ 改编（/upload→/result）→ 短剧（/shortdrama）。
- 一条数据链：Phase1 设定卡 → Phase2 切场景 → Phase3 逐场景转写 → Phase4 合并校验 → 产物落库可回放。
- 演示 40 秒：`/result` 原文对照 + `/debug` 时间线与评分卡（提前打开，别现场跑转换）。

**P4 难点一：长文本**
- 三模式：截断 / 按章 map-reduce / 整本长上下文；一个决策函数，`PHASE1_MODE` 可回滚。
- 设定卡：实体记录称呼出处；场景上下文 = 主角常驻 + 本章在场配角 + 滚动摘要 + 未闭合伏笔。
- 数据：F1 0.752→0.886；召回 10.7→34；溯源 3.97%→96.9%（3 样本 × 3 次）。
- 主动说：归并 token 是截断的 1.5–2.5 倍，短篇仍可能过抽。

**P5 难点二：可靠性**
- 状态落库 + 兼容壳（调用点零改动）。
- 恢复锁：一条 `UPDATE ... WHERE lock_owner IS NULL OR locked_at < expiry`，`changes > 0` 即抢到；TTL 10 分钟、心跳 TTL/3。
- 恢复只重跑失败场景后重合并；取消贯穿执行链；9 码错误 + 指标 + 事件流 + 单场景回放。
- 主动说：单库 CAS 不是分布式锁；并发写同一 job 数组仍可能丢写。

**P6 难点三：质量工程**
- 链路：预标 → 人工抽检 → 冻结 → 打分；3 次运行 mean±σ；剔除自证运行。
- 决策纪律：翻默认先冻结 R1/R2/R3；最终翻默认登记为"所有者决策覆盖门槛"，写清风险与回滚。
- 结果：文档一致性 12/12、单测 747 例、每次结论带日期与快照链接。

**P7 数据页（图表）**：P1 准确率三样本 before/after；一句解读："收益与截断程度正相关，doupo 只掉 0.014。"

**P8 工程化**：monorepo、双后端、CI 四门禁、Docker、多租户、Key 加密、日志脱敏。

**P9 边界**：Agent 工具链未接线（框架就绪，差"把工具定义发给模型"一跳）；样本 3 本全 train；Phase2 最弱 0.556–0.703；PG 未真实联跑。

**P10 下一步**：P2 上下文 3×3 复核 → 扩样本到 30–40 + 20% holdout → judge 盲评校准 → 接通工具调用 → PG 联跑。

**P11 收尾三句**：① 上下文管理是核心资产；② 可靠性靠"落库 + CAS + 可回放"；③ 质量靠"先建度量，再改 prompt"。

## 三、必问 10 问（答法）

1. **为什么不用 LangChain 之类？**
   "需求是可控的状态转移 + 全量落库 + 人工介入，框架把这三件事藏在内部。不过我没做过框架对比，这是取舍不是结论。"
2. **3 个样本，数据可信吗？**
   "够支撑方向，不够支撑显著性。所以我们报 mean±σ、剔除自证运行，并明确标注样本全是 train、没有 holdout。"
3. **F1 0.752→0.886 是不是调 prompt 调出来的？**
   "不是单点调参：主因是截断导致后段实体丢失，换路径后召回回来了（10.7→34）。prompt v2 只把 doupo 的差距从 0.22 收窄到 0.09。"
4. **为什么 Phase2 最弱？**
   "场景边界依赖段落语义，中文长段没有空行分隔，模型对阈值敏感；我们已经定位并修了一处'逐章角色上下文两套语义'的 bug，单次 0.605→0.640，还要 3×3 复核。"
5. **多实例部署怎么办？**
   "数据库共享时 CAS 锁可用；SSE 是进程内 Map、预算计数也不跨进程，多实例会降到轮询、预算上限放大 N 倍——已在文档和启动告警里写明。"
6. **Agent 能自己调工具吗？**
   "不能。工具注册表、8 个工具、执行器、日志都写好了，但工具定义没发给模型，所以每个阶段实际是一次 LLM 调用。补这一跳大约半天。"
7. **成本多少？**
   "价格表按 token 估算，真实花费约为账面 Phase1 的 2–3 倍；9 次基线实测约 ¥1–1.5。守卫只保证不超预算，不保证省。"
8. **最大的坑？**
   "同一类文本形态假设错了三次（CRLF、空行分段、章号语义），修到第三次才建输入形态矩阵；另一个是自证运行让评测虚高。"
9. **如果重做？**
   "先建评测与口径，再写管线。这轮其实就是回头补的：金标注、判据、快照都是后补的。"
10. **商业化怎么落？**
    "B 端改编预演 + 按量计费；可信度卖点是溯源与评测；本期明确不做 AI 出图/成片。"

## 四、演示脚本（60 秒版，提前用本地数据）

1. `/result/<jobId>`：左原文右剧本，点一个场景看 `sourceRefs` 溯源。
2. 改一句对白 → 保存 → 重新校验（展示"可局部修复"）。
3. `/debug`：任务指标卡 + 执行时间线 + 单场景回放。
4. `/shortdrama`：同一剧本的分镜表与导出。
5. 结束语："每一步产物都落库，失败场景带错误码，可以回放对比。"

> 演示前检查：dev server 已起（:3001）、准备 1 个 completed job、不要在现场跑完整转换（3 分钟起步）。
