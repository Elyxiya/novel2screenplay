# 请求落库与双后端存储

> 关联图：[数据流-双后端存储.svg](./数据流-双后端存储.svg)

解释「一次请求如何经过契约校验、业务引擎，最终落到 SQLite / PostgreSQL 之一」，以及双后端引擎的探择与隔离策略。

## 落库主链

```
API 路由层 → 业务引擎层 → 存储适配层（repository） → 引擎探择 → 目标数据库
```

| 层 | 说明 |
|---|---|
| API 路由层 | `/api/pipeline · /api/drama · /api/writer · /api/agent · /api/result` |
| 业务引擎层 | pipeline 四相、drama 分镜引擎、multi-agent 编排、sse 实时推送 |
| 存储适配层 | repository：job / novel / drama / history / agent-task / user / writer-novel / user-llm |
| 契约校验 | `@novel/contracts` zod-4：novel / screenplay / drama / pipeline |

## 引擎探择

```
DATABASE_URL 存在 且 healthCheck 通过  →  PostgreSQL（自动 applySchema）
                                         否则优雅回退  →  SQLite（better-sqlite3）
```

- **SQLite**：默认后端，better-sqlite3，无外部依赖。
- **PostgreSQL**：可选后端，`pg` 驱动 + Atomics 桥（跨线程同步执行），自动建表 `schema-pg`。
- 探择逻辑位于 `db.ts`：先 healthCheck 探活，再决定启用 PG 并应用 schema。

## 双后端隔离

- **测试隔离**：参数化测试经 `resolveTestPgUrl` 路由到 `_test` 后缀库（或 `PG_TEST_DATABASE`），DB 级隔离，绝不写入生产库。
- **单测隔离**：`NODE_ENV=test` 下强制走 SQLite 底座；PG 覆盖由 dual-backend 参数化套件承担，二者互不污染。
- **契约对齐**：schema-parity 校验 SQLite 与 PG 的表/列/约束/索引/外键一致性（如 DOUBLE PRECISION、时间戳→BIGINT）。

## DbEngine 抽象

- `@novel/db` 提供统一同步接口：`prepare().run / get / all`。
- 引擎访问一律经 `getEngine()`（engine-registry），而非直接 `getDatabase()`。
