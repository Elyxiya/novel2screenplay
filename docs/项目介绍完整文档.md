# Novel2Screenplay 项目介绍

> 版本：v0.1.0 | 最后更新：2026-06-10

---

## 一、项目目的

**Novel2Screenplay（小说转剧本）** 是一款基于 AI 的小说转剧本工具，旨在利用大语言模型（LLM）将叙事性小说内容自动转换为标准剧本格式。项目服务于两类核心用户群体：

| 用户群体 | 需求 |
|---------|------|
| **编剧 / 影视创作者** | 需要快速将小说 IP 转化为剧本初稿，评估改编可行性 |
| **网文作者** | 希望将自己的小说可视化，探索影视化改编的可能性 |

### 核心目标

- **自动化**：将耗时的小说→剧本人工转换过程自动化，降低创作门槛
- **结构化**：输出格式化的 YAML 剧本，便于后续编辑、版本管理和交付
- **可追溯**：每个剧本元素附带原文引用（`sourceRefs`），确保可信度和审计能力
- **可编辑**：提供可视化编辑器，让用户对 AI 输出的结果进行人工精修

### 项目背景

项目从 2026-06-05 开始，经历了约 5 天的高强度开发（截至 2026-06-10），由单人完成。技术栈选用 Next.js 16 + React 19 + TypeScript，LLM 集成选用 DeepSeek（主要）和 OpenAI（备选），输出格式选用 YAML + Zod 校验。

## 三、项目核心功能

### 3.1 小说解析与上传

| 功能 | 说明 |
|------|------|
| **文件上传** | 支持 `.txt` / `.md` 文件，自动检测编码（UTF-8 → GBK 回退） |
| **文本粘贴** | 直接粘贴小说文本 |
| **YAML 导入** | 导入已有的 YAML 剧本，支持 dry-run 预览 |
| **章节识别** | 7 种正则模式覆盖中文/英文章节标记，自动回退段落数分割 |
| **编码处理** | 解决 Windows 中文用户 GBK 编码问题，添加 BOM 支持 |

### 3.2 四阶段 LLM 流水线

**Phase 1 - 角色与地点分析**
- 将小说全文送入 LLM，提取角色（含别名/性格标签/描述）和地点（含类型/描述）
- 输出附加时间线提示（时段、跳转、季节）

**Phase 2 - 场景切割**
- 逐章处理，LLM 根据时间/地点/角色变化识别场景边界
- 输出每个场景的起始段落、结束段落、草稿 Slugline、关键角色
- **章节局部坐标**：场景偏移基于章节内计算，避免跨章冲突

**Phase 3 - 场景转换（核心）**
- 并行转换所有已识别场景（信号量限制 3 并发）
- Token Bucket 限流：50 请求/分钟
- 单场景超长时自动拆分：段落级 → 句子级 → 字符分块（~4000 字符/块）
- 每个场景最多重试 3 次，失败时降级输出（`degradedScene`）
- 严格的防幻觉 Prompt：只写可见可听的动作、对白必须源于原文

**Phase 4 - 合并与校验**
- 角色去重：Levenshtein 距离 + 包含关系判断
- 地点去重：名称相似度匹配
- ID 引用解析：将 Phase 3 输出的角色/地点引用映射到规范化 ID
- 改编统计计算：对白占比、动作占比、平均场景长度等
- 自动交叉引用修复：自动创建缺失的角色/地点占位条目

### 3.3 可视化编辑器

**场景编辑器**
- 编辑 Slugline、时间段、地点、摘要
- 对内容块（动作/对白）进行增删改
- 自动从对白块推导角色列表
- 保存前后端双向校验（Zod + YAML 序列化验证）
- 保存时有竞态条件保护（`draft.sceneNumber !== scene.sceneNumber` 检查）

**角色编辑器**
- 编辑角色名称、别名、描述、主要/次要标记
- 支持删除角色（PATCH API 删除实体）

**地点编辑器**
- 编辑地点名称、类型（内景/外景/抽象）、描述
- 支持删除地点

### 3.4 原文对照

- 三种视图模式：对照（分屏）/ 剧本 / 原文
- 左侧展示剧本内容（动作斜体、对白标注角色）
- 右侧展示对应原文摘录（通过 `sourceRefs` 关联）
- 颜色编码：动作→黄色背景、对白→绿色背景

### 3.5 历史记录系统

- 基于 `localStorage` 持久化
- 每次转换完成后自动保存
- 历史条目包含：作品名、场景数、角色数、地点数、创建时间
- 支持从历史记录一键跳转到结果页
- 支持重新上传相同内容继续编辑

### 3.6 其他功能

- **章节选择器**：配置页可选择需要转换的章节，支持跳过无关章节节省 Token
- **费用预估**：基于 tiktoken 精确估算 Token，结合模型单价计算费用
- **多模型支持**：DeepSeek（默认）/ OpenAI 双 Provider
- **任务恢复**：失败任务可从 Phase 3 恢复，只重新转换失败场景

## 四、项目核心功能实现

### 4.1 LLM 抽象层

文件：`src/lib/llm/`

```
BaseProvider.ts   抽象基类（超时 30s、2 次重试、流式 SSE 解析、Token 估算）
DeepSeekProvider.ts  DeepSeek API 实现
OpenAIProvider.ts    OpenAI API 实现
registry.ts          Provider 注册中心（按环境变量自动注册）
rate-limiter.ts      Token Bucket 限流器（50 req/min）
prompts/             提示词模板（含防幻觉约束）
  analyze.ts         Phase 1 提示词
  segment.ts         Phase 2 提示词
  convert-scene.ts   Phase 3 提示词（核心）
```

关键设计：
- **抽象基类模式**：`BaseProvider` 封装所有 HTTP 层面逻辑（超时、重试、流式解析），子类只需实现 `chat()` 和 `chatStream()`
- **组合式 AbortSignal**：将外部取消信号和内部超时信号组合，任意一方触发即中止
- **动态导入 tiktoken**：防止 wasm 文件在服务端路由初始化时加载失败

### 4.2 流水线编排

文件：`src/lib/pipeline/PipelineEngine.ts`

```
PipelineEngine
  ├── startJob()       # 创建任务、异步启动流水线
  ├── resumeJob()      # 恢复失败场景（从 Phase 3 重跑）
  ├── cancelJob()      # 重置任务状态
  ├── getJobStatus()   # 返回当前任务状态快照
  └── runPipeline()    # 内部：顺序执行 Phase 1→2→3→4
```

关键设计：
- **异步非阻塞**：`startJob()` 启动流水线后立即返回 jobId，流水线在后台 Promise 中运行
- **细粒度状态更新**：每阶段更新 `status`、`currentPhase`、`progress`、`scenesStatus[]`
- **日志系统**：每个关键步骤写入结构化日志（时间戳+级别+消息），支持前端实时展示

### 4.3 全局状态管理

文件：`src/lib/store/job-store.ts`

```typescript
// 核心技巧：通过 globalThis 挂载，绕过 Next.js HMR 重新初始化
const GLOBAL_KEY = '__novel2screenplay_jobStore';
function getGlobalStore(): JobStore {
  if (!(globalThis as any)[GLOBAL_KEY]) {
    (globalThis as any)[GLOBAL_KEY] = new JobStore();
  }
  return (globalThis as any)[GLOBAL_KEY];
}
```

- 内存 Map 存储 + `globalThis` 挂载防止热重载丢失
- 严格的恢复锁管理（`recoveringJobs` Set + `tryLockRecover`）
- 不可变更新模式：`update(id, updater)` 接受回调函数

### 4.4 JSON 解析健壮性

文件：`src/lib/utils/safe-json.ts`

四层降级策略：

| 策略 | 说明 |
|------|------|
| 1. 直接解析 | `JSON.parse(text)` — 最快路径 |
| 2. 剥离 Markdown 代码块 | 移除 ` ```json ` 等包裹标记 |
| 3. 括号匹配提取 | 找到第一个 `{`→`}` 或 `[`→`]` 对，提取内容解析 |
| 4. 清理垃圾字符 | 移除尾随逗号、修复未引号键名、替换单引号、移除控制字符 |

截断检测（`looksTruncated`）：若 content 数组只有一个超长（>3000 字符）块，判定为截断并触发重试。

### 4.5 Schema 与校验体系

文件：`src/lib/schema/`

```
screenplay.schema.ts  →  Zod Schema 定义（含 discriminatedUnion）
validator.ts           →  validateScreenplay() + autoFixScreenplay()
yaml-serializer.ts     →  YAML ↔ Screenplay 序列化/反序列化
```

核心设计决策：
- **Discriminated Union**：对白（DialogueBlock）和动作（ActionBlock）通过 `type` 字段区分，TypeScript 自动推导分支类型
- **ID 引用范式**：角色和地点独立列表，场景通过 `characterId` / `locationId` 引用
- **自动修复**：`autoFixScreenplay()` 自动创建缺失的角色/地点占位条目，确保数据完整性
- **YAML 作为交换格式**：YAML 的可读性优于 JSON，支持注释和块标量字符串

### 4.6 前端编辑器

以 `SceneEditor.tsx` 为例的关键实现细节：

- **编辑态/预览态**：通过 `editing` 状态切换，非编辑时只读展示
- **Draft 模式**：修改在本地 draft 中进行，用户"保存"时才提交
- **竞态条件防护**：保存时检查 `draft.sceneNumber !== scene.sceneNumber`，防止切换场景后错误覆盖
- **自动推导角色列表**：从所有对白块的 `characterId` 去重生成 `characterIds`
- **内容清理**：保存前过滤空内容块（空 action 描述/空对白）
- **PATCH API 双路径**：既支持批量替换（`body.scenes` / `body.characters` / `body.locations`），也支持单实体更新（`body.scene` / `body.character` / `body.location`）和删除（`body.deleteCharacterId` / `body.deleteLocationId`）

## 五、项目困难、取舍与解决方案

### 5.1 LLM 输出不可靠性

**困难**：
- LLM 输出的 JSON 格式不固定：有时带 markdown 代码块，有时遗漏引号，有时尾随逗号
- LLM 会"幻觉"原文不存在的内容：添加原文没有的对话、角色、情节
- LLM 输出可能因 maxTokens 被截断，导致 JSON 不完整
- LLM 即使要求 `json_object` 模式，仍可能返回非 JSON 内容

**取舍**：
- 我们选择了 **"宽松解析 + 严格重试"** 策略：先尽最大努力解析，解析失败则重试，重试耗尽则降级
- Prompt 设计上我们加入了大量 **负面约束**（"不要做 X"），而不是仅写正面指令

**解决方案**：
1. **`safeJsonParse` 四层降级**（见 4.4 节）
2. **防幻觉 Prompt**：明确要求"只写可见可听的动作"、"只保留原文有引号的对白"、"心理活动不转为 action"
3. **`looksTruncated` 截断检测**：单块超长内容自动重试
4. **重试机制**：Phase 1/Phase 3 最多重试 3 次，指数退避等待
5. **降级输出**：所有重试失败后输出 `degradedScene`，包含失败原因

### 5.2 跨章节场景偏移冲突

**困难**：
- Phase 2 的场景偏移使用全局字符索引（从小说第一个字符开始算起），但每个章节内部都从 0 开始
- 当 Phase 3 用 `scene.originalStartOffset` 和 `scene.originalEndOffset` 从 `chapterTexts[chapterIndex]` 切片时，跨章场景的偏移全部错位
- 全局去重策略在章节边界处会把前一章的尾和后一章的头判定为"重叠"并错误删除

**解决方案**：
1. 切换为 **章节局部坐标**：每个章节内部的偏移从 0 开始计算（`calculateCharOffsets` 逐章独立调用）
2. 修改重叠解析策略：从全局 `resolveOverlappingBoundaries` 改为 **逐章解析** `resolveOverlappingPerChapter`——按 `chapterIndex` 分组后分别处理
3. Phase 3 的切片逻辑保持不变（从 `chapterTexts[scene.chapterIndex]` 按局部偏移切片），因此改动只影响 Phase 2

```typescript
// Phase2Segmenter.ts:resolveOverlappingPerChapter
// CRITICAL: 按章节分组解析，不允许跨章重叠判定
const byChapter = new Map<number, SceneBoundary[]>();
for (const scene of scenes) {
  const list = byChapter.get(scene.chapterIndex) ?? [];
  list.push(scene);
  byChapter.set(scene.chapterIndex, list);
}
// ... 每个章节独立排序、独立去重
```

### 5.3 LLM 上下文窗口限制

**困难**：
- 小说章节可能非常长（>10 万字符），超出 LLM 上下文窗口
- 单场景也可能包含大量文本，需要拆分

**解决方案**：
1. **Phase 1 Token 管理**：`truncateToTokens(text, 30000)`——超出 3 万 token 时按比例截断
2. **Phase 2 Token 管理**：`truncateToTokens(text, 8000)`——逐章处理，每章限制 8k token
3. **Phase 3 场景拆分**：三重策略
   - 段落级拆分：按空行分段，~4000 字符一组
   - 句子级回退：按句号拆分，~4000 字符一组
   - 字符级回退：直接按 4000 字符切分
4. **maxTokens 逐步提升**：从 8192 → 16384（commit `9836102` → `db44fdd`）

### 5.4 Next.js 热重载状态丢失

**困难**：
- `jobStore` 是一个 `Map<string, StoredJob>` 的内存实例
- Next.js 开发模式下，模块热重载会导致模块重新执行，Map 内容全部丢失
- 用户正在进行的转换任务中断

**解决方案**：
- 将 `jobStore` 实例挂载到 **`globalThis`**（Node.js 的全局对象，热重载不会重置）
- 使用唯一键 `__novel2screenplay_jobStore` 避免命名冲突

```typescript
const GLOBAL_KEY = '__novel2screenplay_jobStore';
function getGlobalStore(): JobStore {
  if (typeof globalThis !== 'undefined') {
    if (!(globalThis as any)[GLOBAL_KEY]) {
      (globalThis as any)[GLOBAL_KEY] = new JobStore();
    }
    return (globalThis as any)[GLOBAL_KEY];
  }
  return new JobStore(); // fallback
}
```

**取舍**：
- 这是 **V1 的已知限制**：内存存储在多实例部署下不共享。README 明确标注此限制，并计划后续迁移到 SQLite/Redis
- 选择轻量的内存方案而非数据库，是因为 V1 阶段聚焦于单机快速迭代，避免基础设施开销

### 5.5 中文编码问题

**困难**：
- 中国 Windows 用户大量使用 GBK/GB2312 编码保存 `.txt` 文件
- Node.js 的 `TextDecoder` 默认只支持 UTF-8，直接读取 GBK 文件产生乱码
- 错误地将 GBK 文件解析为 UTF-8 后，中文会变成不可读字符

**解决方案**：
1. 使用 `TextDecoder('utf-8', { fatal: true })` 先尝试 UTF-8 解码
2. 失败后使用 `iconv-lite` 库以 GBK 解码
3. 解码后检测是否包含替换字符（`�`）或空字符
4. 输出文件时添加 **UTF-8 BOM**（`0xEFBBBF`），解决 Windows 记事本显示乱码

### 5.6 中文特定挑战

| 挑战 | 解决方案 |
|------|---------|
| 中文章节标记多样性 | 7 种正则模式：`第X章` `序章` `Chapter X` 等 |
| 序章/尾声特殊处理 | 增加 `^\s*序\s*[：:]` 模式匹配，前导空格支持 |
| 中文句号分割 | `splitBySentenceBoundaries` 使用 `(?<=[。！？\n])` |
| 角色名相似度 | Levenshtein 距离（阈值 0.3）+ 包含关系判断 |
| timeOfDay 中文映射 | 18 种中英文时间表述映射到 7 个标准枚举值 |

```typescript
// timeOfDay 中英文映射表
const TIME_OF_DAY_FALLBACKS: Record<string, string> = {
  day: 'afternoon', 白天: 'afternoon', 早上: 'morning',
  黄昏: 'dusk', 夜晚: 'night', 深夜: 'late-night',
  // ... 共 18 项映射
};
```

### 5.7 并行转换的并发控制

**困难**：
- Phase 3 需要并行转换数十个场景以提升速度
- 但 LLM API 有限流限制，且大量并发请求可能触发 HTTP 429
- 内存开销随并发数线性增长

**解决方案**：
1. **Semaphore（信号量）**：最大 3 个并发场景转换
2. **Token Bucket 限流器**：50 请求/分钟，超出等待
3. **`Promise.allSettled`**：确保单个场景失败不阻塞整体流程
4. **`AbortSignal` 传播**：任务取消时，正在进行的 LLM 请求通过 AbortSignal 取消

```typescript
// 信号量 + 限流器 + 批量处理
const tasks = scenes.map((scene) => async () => this.semaphore.run(async () => {
  if (abortSignal?.aborted) throw new DOMException('Aborted', 'AbortError');
  await this.rateLimiter.wait(abortSignal);
  // ... 场景转换逻辑
}));
const results = await Promise.allSettled(tasks.map(t => t()));
```

### 5.8 UI 竞态条件与状态管理

**困难**：
- React StrictMode 双渲染导致 `useEffect` 重复执行
- 场景编辑器在切换场景时保存操作可能覆盖错误数据
- 进度轮询和页面跳转之间的时序问题

**解决方案**：
- **SceneEditor 保存保护**：`if (draft.sceneNumber !== scene.sceneNumber) return;`
- **sessionStorage + 空检查**：convert 页不从 sessionStorage 读取数据
- **轮询清理**：`useEffect` 返回清理函数停止轮询
- **历史保存在转换完成时**：在 `status === 'completed'` 时触发 API 获取并保存到 localStorage

### 5.9 npm install 文件丢失问题

在 `d225ee1` 等提交中，`yaml-import-ui` 功能随 `feat/yaml-history` 分支一起开发，但分支合并时发生了冲突和部分文件丢失。项目使用了 **feature branch + rebase** 策略：

- 每个独立功能（`feat/chapter-select`、`feat/editor-delete`、`feat/yaml-history`）在独立分支开发
- 通过 `git merge` 合并回 `main`，同时保持 `dev` 分支作为集成分支
- 合并冲突在 `Merge branch 'main' into feat/xxx — 解决冲突` 的合并提交中解决

### 5.10 重要技术取舍总结

| 决策 | 选择 | 考虑过的替代方案 | 原因 |
|------|------|-----------------|------|
| **存储方案** | 内存 + globalThis | SQLite / Redis / 文件系统 | V1 快速迭代，避免基础设施开销 |
| **LLM Provider** | DeepSeek（默认）+ OpenAI | 仅 DeepSeek / 仅 OpenAI | DeepSeek 成本低、中文好；OpenAI 备选 |
| **输出格式** | YAML + Zod 校验 | 纯 JSON / Markdown | YAML 人类可读、Git diff 友好 |

| **Schema 类型系统** | Zod discriminatedUnion | 手动类型守卫 / io-ts | Zod 提供解析 + 校验 + 类型推导一体 |
| **流水线状态管理** | 内存 Map + 不可变更新 | Redux / Zustand / XState | 简单够用，less is more |
| **防幻觉策略** | Strict Prompt + 降级输出 | 后处理过滤 / 多模型投票 | Prompt 成本最低、效果最直接 |
| **测试策略** | Vitest + MSW | Jest / Playwright / 无测试 | Vitest 与 Next.js 兼容性好 |

## 八、总结

**Novel2Screenplay** 是一个功能完整的 AI 小说转剧本工具，在约 5 天的开发周期中完成了从 Schema 设计到可视化编辑的全链路实现。项目面临的核心挑战包括：

1. **LLM 不可靠性的系统化应对** — 通过多策略 JSON 解析、防幻觉 Prompt、截断检测、重试/降级机制，将 LLM 的不确定性控制在可接受范围内
2. **中文内容的特化处理** — 中文编码检测、章节标记多样性、时间表述映射、角色名相似度算法
3. **工程健壮性** — 全局共享状态应对热重载、并发控制（信号量+限流器）、竞态条件防护、细粒度状态追踪

项目的设计哲学是 **"AI 辅助而非替代"**：AI 完成初稿转换，但输出格式（YAML）和可视化编辑器确保人类可以轻松审阅和精修。sourceRefs 溯源机制为 AI 输出提供了可验证性，是建立用户信任的关键设计决策。
