## 术语表

同一个词在不同章节必须指同一件事。先对齐再讨论：

| 术语 | 含义 | 对应字段 / 实现 |
|---|---|---|
| **在场** | 场景里实际出现的人，**允许未点名**（如「戴玉坠的少女」） | `keyCharacterNames` |
| **提及** | 对话/背景里说到、但人不在场（云韵、纳兰桀） | `mentionedCharacterNames` |
| **场景级指代** | 本场之内对某人的称呼，单向、不参与匹配（「这一场的中年男子」） | `characterRefs[].referredAs` |
| **别名** | 双向同一性：提到它就是这个角色（薰儿 ↔ 萧薰儿） | `characters[].aliases` |
| **描述性实体** | 以「外观/身份描述」命名的实体（中年男子、青衫老者、瓜子脸女孩）；证据不足时**不是角色** | `DESCRIPTOR_ALIAS_RE` |
| **墓碑** | 判为背景后留下的记录（名字 + 理由 + 证据），不参与匹配 | `meta.excludedCharacters` |
| **自证运行** | 金标注由该次运行自己生成；评分时必须剔除，否则 F1 恒为 1 | `checkIndependence` |
| **跨运行一致性** | 重跑会不会变（稳定性） | `baseline.mjs` 的「跨运行」列 |
| **准确率** | 对不对（对 reviewed 金标注） | `baseline.mjs` 的「准确率」列 |
| **金标注 / gold** | 人工抽检过（`reviewed=true`）的 `screenplay-gold/v1` 文件 | `gold.json` |
| **占位率** | 场景里引用了「角色卡之外的名字」的比例 = `review-sheet` 的「未登记出场名」占比 | `phase1-ab.mjs`、`review-sheet.mjs` |
| **章节标签** | `chN(idxM)`：N = 正文 1 基章号，M = 0 基 `chapterIndex`；全库打印章节只用这一种 | `annotation.mjs` 的 `chapterLabel()` |

## 维护约定（持续更新）

这是一份**活文档**：只要本项目的口径或管线变了，它就必须跟着变。三类触发：

| 触发 | 动作 |
|---|---|
| 修了一个非平凡 bug | 在「二、问题全景」加一行，并在「三、分类详解」补一段（含证据数字） |
| 做了一项口径决策（字段语义、字段新增、默认值变更） | 更新对应段落 + 回链到 `gold-annotation-workflow.md` 或 `flip-decision-record.md` |
| 自己踩了坑（误删、编码、误判、循环论证） | 记入「三、E」或对应章节——**失误比成功案例更值得留** |

每次追加后同步检查四处：

1. **原则清单**（第四节）是否需要升级或新增；
2. **未解决事项**（第五节）是否该划掉/新增；
3. **关键数字**（第七节）是否过期；
4. **文件索引**（第六节）是否漏了新模块；
5. 跑一遍 `node scripts/eval/doc-check.mjs`，**必须 12/12 PASS**：
   路径存在、阈值与代码常量一致、开关真实被读取、三份文档互链、文档承诺的规则在实现中存在、
   文档示例的 gold 字段都被校验器覆盖、文档的体检项在 `review-sheet` 中实现、
   「未解决事项」的状态与代码一致、关键数字都带时效标记、三份文档术语一致、维护日志可追溯、
   可调参数表与代码一致；
6. **重大改动后**（改了 Phase1 模式、评分口径、参考卡）跑 `node scripts/eval/snapshot.mjs`
   重新生成快照，并在第七节把链接指向新文件——**不要手抄数字**（手抄必然过期）。

> 一致性红线：文档里写的阈值、默认值、开关名必须与代码一致
> （如 `CHARACTER_SANITIZE`、`SCENE_CHARACTER_GROUNDING`、跨章≥2 / 提及≥3）。
> 改代码时顺手 grep 一下文档里的旧数字，别让文档变成谎言——第 5 步就是这道红线的自动版。

## 一、一句话概要

这轮修的问题里，**真正的新 bug 很少，九成是「实现假设与真实文本/真实语义不一致」**：
以为段落是空行块、以为章号是切片内序号、以为「提到」就是「在场」、以为「描述」就是「别名」、
以为「角色卡里有」就等于「本章出现了」。所以解法尽量落在**口径与校验**上，而不是打补丁。

## 三、分类详解

### A. 文本形态：同一类 bug 出现了三次

**现象**：CRLF 文本切出的场景原文错位、场景大量合并、溯源率极低、章号对不上。

**根因**：实现里假设了「规整文本」——LF 换行、空行分段、章号从 1 连续。
真实网文是 CRLF、单换行成段、章号是原书全局编号。

**解法**：

1. 入口归一：`parseNovel` / `cleanNovelText` 统一 CRLF/CR → LF；
2. 段落口径统一为「**一个非空行**」，prompt 里写死，模型与代码用同一坐标系；
3. 章节号一律用**切片内序号**，不信任模型给的原书章号；
4. 模型行号越界时按比例缩放 + 双向钳制，并打 warn；
5. **兜底路径也要同一口径**：`fallbackSplit`（LLM 失败时）此前按空行分块，
   与主路径「非空行」不一致，段号会指向块序号 → 已抽出 `phase2-fallback.ts` 统一，
   并补 `phase2-fallback.test.ts`（6 条）覆盖行号、字符偏移与 token 分组。

**防复发**：`input-form-matrix.test.ts`（12 条）把
「LF/CRLF/CR × 空行/单换行/无空行 × 5 种章号写法 + BOM/全角缩进/连续空行」
固化成断言——同一份逻辑内容无论以哪种形态进来，章节文本、场景偏移与切片必须一致。

**教训**：同一个假设错误出现三次，就不是偶发 bug，而是**缺少契约**。
应该先建矩阵，再修个案。

---

### B. 语义口径：三个必须分清的区分

这一组是这轮最有价值的沉淀，全部来自人工抽检暴露的问题。

#### B1. 在场 vs 提及

- `keyCharacterNames` = **实际在场**（允许未点名）；
- `mentionedCharacterNames` = **对话/背景里提到、但人不在场**。

**触发**：抽检发现云韵/纳兰桀/古河被判成「孤儿角色」——他们只出现在
「被云韵收为弟子」这类叙述里。按在场判孤儿，就误报了。

**结果**：孤儿角色 6→0；同时 Phase3 构造上下文时只注入在场角色，两个字段不能合并。

#### B2. 别名 vs 描述

- **别名是双向同一性**：「韩晓龙」提到就是白冷叶；
- **描述是场景内单向指代**：「这一场的中年男子是方晓语父亲」≠「所有中年男子都是他」。

**触发**：用户指出「方晓语的父亲是中年男子，并不等于中年男子都是方晓语父亲」。
一查发现同一类错误有 7 处（妇女、青衫老者、黄袍老者、烧伤疤痕老头…）。

**反例（真实数据）**：批量回填时把 13 处「妇女」全映射给豆豆妈，查原文发现
「妇女」在这份文本里至少指 4 个人：白冷叶的母亲（#1/#5）、火车上的陌生妇人（#6）、
豆豆妈（#7/#14/#15）。

**解法**：

- 描述不进 `aliases`；校验器 `DESCRIPTOR_ALIAS_RE` 给 warning；
- 新增 `scenes[].characterRefs = [{ name, referredAs }]`：场景级、单向、不参与匹配；
- 合并只在**同段且紧邻**（间隔 ≤12 字、其间无互动动词）时建立。

#### B3. 在场但未点名

《斗破》第 3 章那位「戴绿色玉坠、三星斗者的少女」就是纳兰嫣然，全章没写名字。
金标注按事实把她计入在场；模型漏标就是真实漏标。

**但反过来不能用它做自动清理**：`groundSceneCharacters` 默认只告警不删除，
因为「名字没出现」既可能是幻觉（豆豆@ch10），也可能是「在场未点名」（萧薰儿@ch7、
白爱玲@ch1 原文写「母亲」）。两者的文本证据完全一样，自动规则区分不了。

#### B4. 背景人物：删了即遗忘

用户抽检判定 8 个描述性实体「只是背景」后，直接删掉会留下一个问题：下次抽检看到同一堆名字，
又会犹豫「这个当初为什么被删」。于是引入**墓碑** `meta.excludedCharacters`：

- 记名字 + 理由 + 章数/提及数证据，**不参与匹配**，只做审计；
- 作用是「样本级」的：角色若在后续章节变重要，属于另一份切片，管线重建卡时会重新抽进来；
- 校验器：同名同时出现在角色卡与墓碑 → warning。

这条也定了「背景」的判定参照：跨章 ≥2 或 提及 ≥3 才算有角色重量。

### C. 管线逻辑

#### C1. Phase1 截断：问题真实存在，但解法不是一刀切

**现象**：`xiuzhen-short` 5.7 万字 / 72k token，上限 30k → 只分析前 41%；
方晓语等后段角色整批没进卡，场景里却被标出来（19 个「未登记出场名」）。

**A/B 结果（对 reviewed 金标注；2026-10-21 刷新到 prompt v2 之后）**：

| 样本 | truncate F1 | mapreduce F1 | 结论 |
|---|---|---|---|
| xiuzhen（41% 被分析） | 0.531 | **0.839** | 受益明显 |
| zhanlan（78%） | 0.737 | **0.923** | 受益 |
| doupo（78%，角色少） | **0.987** | 0.897 | 仍略低，但差距从 0.22 收窄到 0.09 |

**结论**：mapreduce 的收益与**截断程度正相关**；短篇/角色少的样本仍可能因过抽而略低，
但 prompt v2（候选池改为本章原文）已把差距大幅缩小。所以翻默认应按长度分流，而不是全局切换。

**纪律**：仓库有预注册门槛 `decidePhase1Flip`（R1/R2/R3），判据是尾段占位率/judge 分层，
不是 F1。本组数据不触发，`flip` 维持 `false`——**不许用别的指标绕过既定判据**。

#### C2. Phase2 的角色选择：候选池错了

**现象**：第 10 章原文一次没提「豆豆」，Phase2 却在三个场景里都标了他。

**根因**：模型从**角色卡**里挑人，卡里有谁就可能被带进没出现他的章节。

**解法**：prompt 要求 3 改为「候选池 = 本章原文实际出现的人物；角色卡只用于把称呼归一成规范名」。

**结果**：豆豆、马六男消失；doupo Phase1 精度 0.619→0.813。

#### C3. 描述性实体：证据门槛 + 不合并 + 级联

**现象**：mapreduce 后角色卡 10→34，混入「月白衣袍老者」「瓜子脸女孩」，精度 0.91→0.32。

**解法**（`character-sanitizer.ts`）：

1. 描述性实体 +（跨章 ≥2 或 提及 ≥3）→ 保留；否则移出卡；
2. 证据**只取章节原文**——不取 Phase2/Phase3 输出，否则像大副（#11 被漏标）
   这种真角色会被连带误杀；
3. 描述永不并入具名角色；删除必须级联清理场景引用；
4. `CHARACTER_SANITIZE=off` 可整体回滚。

**注意**：当时看到的 0.32 主要不是描述性实体造成的，而是**参考卡不全**（见 D1）。
参考卡补齐后，xiuzhen mapreduce 的精度回到 **0.743**（2026-10-21 实测），残差来自漏抽（胖妹）。

#### C4. Phase3 的「有声书化」

背景解释（谁是谁的爷爷）不得写成 action，只能由在场角色逐字对白交代。
实测改前 action 块里的关系断言已经是 0，所以这次是**护栏**，不是修 bug——
但它把「不许做」写死，防止后续调 prompt 时回退。

### D. 评测方法

#### D1. 参考卡不全 → 精度虚低（这条差点误导决策）

一开始 mapreduce 的 xiuzhen 精度只有 0.32，看起来「过抽严重」。
补齐参考卡（补进韩夫人、郭强、李方法等真实配角）后重算：**mapreduce F1 0.820、truncate 0.531**，
结论直接反转。

**教训**：precision 低先检查参考集是否完整，别急着怪模型。

#### D2. 循环论证

金标注如果来自被评的那次运行，分数天然是 1.0（run1 的 P2 F1=1.0 就是自标）。
聚合时必须**剔除自证运行**，否则稳定性被高估。代码里 `checkIndependence` 会提示。

#### D3. 稳定性 ≠ 准确性

- 「跨运行一致性」回答「重跑会不会变」；
- 「准确率」回答「变得对不对」。

两者要分开报。早期用单次运行对比判「角色数 8 vs 13，不稳定」，三次后是 12.7±0.6——
**单次采样会制造假象**。

#### D4. judge 目前不能做决策

三个样本 55–85 分，σ 最高 13，且与结构指标不同向（场景最细的样本 judge 最低）。
在人工盲评校准（Spearman ρ）之前，它只能当参考。

## 四、可复用的判断原则

1. **先问「这是口径问题还是实现问题」**。口径问题改契约，实现问题改代码——反了就会反复打补丁。
2. **同一个 bug 出现两次以上，就建矩阵/契约**，别修第三个个案。
3. **证据只取上游原文**。用下游输出做判定会形成循环（拿 Phase2 的标签去判角色是否存在）。
4. **删除是最危险的动作**。默认「标记/告警」，`enforce` 才真删，且必须可回滚、幂等、级联。
5. **合并要保守**。错合并（路人变主角）比漏合并更难发现，指标上也看不出来。
6. **改默认要有预注册判据**。指标不能事后挑；不满足就维持现状，并如实记录「缺数据」。
7. **先测基线再改**，单变量；报告 mean±σ，不用单次运行下结论。
8. **把「不许做」写进 prompt 的硬约束**，哪怕当前违规率是 0——它是给未来改动的护栏。
9. **人工抽检不可省**。模型自评、judge 分数、离线复算都不能替代「人看一眼原文」。
10. **不要静默回退**。读不到数据就告警或报错；`?? fallback` 会让同一指标出现两个数
    （溯源 95.1% vs 95.4% 就是这么来的），而且没人会发现。已给 `score.mjs` / `baseline.mjs` /
    `review-sheet.mjs` / `phase1-ab.mjs` / `snapshot.mjs` 的回退与缺失路径加 `console.warn`。
11. **系数要有实测出处**。`length * 0.6` 估 token 低估约 2.2 倍（实测中文 1.3–1.4 token/字），
    成本守卫因此长期虚低。任何「经验系数」都要注明测量来源，否则它会安静地错很久。
    已改为 `estimateInputTokens()`（tiktoken 实测，失败回退 1.3 并告警）。
12. **批量实验先小跑再放量**。9 次实验前先跑 1 次、看实测耗时与花费，再决定要不要 3×3；
    `--cost-cap-cny` 只是**Phase1 输入**的红线，真实花费约为其 2–3 倍（见第 36 条）。

**审计发现（第 21 条问题）**：第 8 条此前**没有内容断言**——两条 prompt 改坏了测试也全绿，
只有 token 预算断言在起作用。已补：

`segment-prompt.test.ts` 锁「本章原文实际出现 / 不是候选池 / 宁可少写 / 非空行」。

> 教训：**「写在 prompt 里的约束」也要有测试**。prompt 不是代码，改它不会有类型错误，
> 只会在几周后以「模型变笨了」的形式暴露。断言关键词是成本最低的护栏。

> 工具也要被验证：`doc-check.mjs` 第一版对阈值只做了 `text.match`（只取第一处），
> 而文档里同一阈值会在页首红线与正文各出现一次——页首对、正文错时它照样 PASS。
> 改成 `matchAll` 全量比对后，变异测试才真正报红。**任何「检查器」都要先被变异测试咬一口。**

> 检查器最危险的失败不是报错，而是**静默通过**。这一轮又踩了两次：
> ① CRLF 让围栏正则失配，解析出 0 个字段，却仍报 PASS（现在空结果直接判 FAIL）；
> ② 用 `includes` 判标识符，`tinyScenesRenamed` 因为「包含」`tinyScenes` 被判成存在
> （现在用边界匹配 `hasToken`）。经验：**每加一类检查，先造一个必然失败的变异**，
> 并确保「什么都没解析到」时判 FAIL 而不是 PASS。

> 变异测试的操作顺序也有坑：用 `git checkout` 恢复被变异的文件时，会**连带回滚同一文件里
> 未提交的改动**。这一轮就这样把刚写好的日期标记冲掉了，只能重做。
> 正确做法：**先把正常改动提交，再做变异**；或者对副本做变异，别动工作区里的目标文件。

> 检查器也会误报：术语黑名单把「维护日志里记录改名历史」当成了违规使用。修法是**排除日志区**——
> 检查器要区分「正文里的用法」和「历史记录里的引用」。同时记一条流程纪律：
> **检查没过就不提交**（这次就是 9/10 时没细看直接 commit 了）。
