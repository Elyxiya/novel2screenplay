## 条目 1 · LLM 输出的容错解析

> 做 LLM 结构化输出时遇到两个问题。一是输出格式不稳定：带 Markdown 围栏、尾随逗号、单引号当键名，直接 `JSON.parse` 会失败。二是更隐蔽的——解析函数为了不崩上游，失败时返回一个带 `_parseError` 标记的哨兵对象而不是抛错；调用方只要漏检这个标记，就会把"解析失败"当成"合法的空结果"，重试逻辑永远不触发，长篇小说的角色卡会静默丢光。
>
> 我的处理：解析器保留四层降级（直接解析 → 剥离围栏 → 括号配对提取 → 清理垃圾字符），失败返回哨兵；然后在 Phase1 的调用点显式拦截哨兵并主动抛错，让 3 次重试真正生效。对"只有一个内容块且长度超 3000 字"的输出判定为被 `maxTokens` 截断，同样抛错重试。重试间隔按 1s / 2s / 3s 递增（线性，不是指数）。3 次都失败不抛到任务层，而是输出一条带错误码和 `confidence 0.1` 的降级场景，让失败的场景留在产物里可以被筛出来，而不是整条任务失败。

**【可追问点】**
- "解析失败为什么用哨兵而不是直接抛错？" → 预期你能答出：解析器被多处复用（Phase1/2/3、场景重写），抛错会让所有调用方都必须写 try/catch；哨兵把"是否值得重试"的决定权交给调用方。代价就是你刚踩的那个坑——漏检。
- "四层降级里哪一层最常命中？" → **如果你没统计过，直接答"没有统计，我只验证过能覆盖哪些畸形形态"**。别编。

**【风险项】**
- 退避是 **1s / 2s / 3s 线性递增**。旧简历写的"指数退避"是错的，改掉。
- "3000 字"和"3 次重试"是代码里的阈值常量，不是测出来的经验值。被问"为什么是 3000"要答："单块超长是截断的特征，这个值是拍的；没有做过不同阈值的对比。"
- "降级场景留在产物里"这句要能说清：降级内容是一条 `[场景转换失败: 原因]` 的占位 action，`confidence` 固定 0.1，失败原因分类成 9 个错误码之一。

## 条目 2 · 长文本的上下文管理

> 小说动辄几十万字，整本塞不进上下文，早期做法是"按比例截断到 3 万 token 再送一次分析"。这个做法的毛病是截断位置会落在句子中间，而且**后半本书的角色和地点直接不参与分析**。
>
> 我加了另外两条路径：一条是按章并行抽取（每章抽出角色/地点/时间线/章节摘要/开放伏笔），再跑一次归并把这些结果合并成全局设定卡，归并时每个实体记下"这个称呼是从哪一章并进来的"以便回溯；另一条是把整本不截断送进大窗口模型。三条路径都保留，切换靠一个独立的纯函数决策点，判据写成返回的常量以便审计，**数据不够时它返回"不切换"**。默认仍走截断基线，因为我没有做出能证明更优的对照数据。
>
> Phase3 组装每个场景的上下文时，也从"整张角色表塞进去"改成：主角卡常驻 + 配角只注入本场景在场名单里命中的、前 5 章的滚动摘要、按章节区间筛选未闭合的伏笔。这样 prompt 体积不再随全书角色数增长。

**【可追问点】**
- "归并怎么判断'张三'和'张三丰'是同一个人？" → 预期答：归并这一步把判断交给 LLM（让它输出归并分组），而不是规则；规则只做**归并前的冲突预警**（别名撞车、循环别名、同名跨章 30 章以上且标签无交集），且明确只预警不裁决。
- "为什么默认不走 map-reduce？" → 这是加分题，答：map-reduce 每章一次调用，成本是基线的 N 倍（N = 章数）。所以我把"是否翻默认"做成独立决策模块，要有实测数据门槛才翻，避免凭感觉切。

**【风险项】**
- **绝对不要说"解决了长文本丢失"或"提升了质量"**。你没有截断版 vs map-reduce 版的对照数据。只能说"提供了逐章抽取的路径，避免整本截断导致后半段实体不参与分析"。
- **默认模式是截断基线**。如果说成"已切换到 map-reduce"，被打开代码一看就露馅。
- `docs/conversion-quality/` 下的评测曲线相关材料里，`jd-coverage.md` 自己就写了"曲线尚未出数"、"**不写曲线判定通过/已验证**"。如果你要引用评测，只能讲机制（身份断言三条规则、稳定性报告、基准样本集），不能讲结论。

## 条目 3 · 任务状态的持久化与断点恢复

> 任务状态原先放在内存 Map 里，用 `globalThis` 挂载来躲 Next.js 热重载导致的模块重执行。问题是重启就丢、多实例不共享，而且用户看到的"任务丢了"没有任何补救路径。
>
> 我把状态落到 SQLite，但**保留原来的类和方法签名做兼容壳**，内部转调 repository，这样几十个调用点一行不改。恢复锁也从进程内的 `Set` 换成了数据库层的 CAS：用一条 `UPDATE ... WHERE lock_owner IS NULL OR locked_at < 过期时间` 实现，靠 `changes > 0` 判断是否抢到锁，不需要事务；锁带 10 分钟 TTL，长恢复期间按 TTL/3 打心跳续锁，进程崩了锁会自己过期被别人抢走。
>
> 恢复逻辑本身也重做了：原来失败后是"重跑全量"，现在只挑出 failed 和 pending 的场景重跑 Phase3，再按场景号与旧产物对齐合并、重跑 Phase4。另外修了一个集成测试抓到的状态覆盖 bug：重转路径一进来就把任务状态写成"转换中"，重转结束后没人写回终态，任务会永远卡在转换中——现在收尾显式写回 completed。

**【可追问点】**
- "为什么用一条 UPDATE 当锁，不用 Redis 或者 `SELECT FOR UPDATE`？" → 预期答：单库场景下 CAS 语义就够——"锁为空或已过期"作为 WHERE 条件，`changes` 就是原子性的证明，省掉一个外部依赖。**要主动承认边界**：这是单库 CAS，不是分布式共识；多副本共享同一个库时可用，分库不行。
- "TTL 为什么定 10 分钟？" → 答"拍的，没有压测依据；心跳周期取 TTL/3 是为了在锁过期前至少续两次。" 别说是根据恢复耗时算出来的。

**【风险项】**
- **不要写"分布式锁"或"高可用"**。这是单库 CAS + TTL。
- 代码注释里 `resumeJob` 上还留着 `TODO: Re-run Phase 3 for failed scenes only`，但**实现已经做了**。面试官若打开代码看到这条注释会问"这个 TODO 做没做"——你要能立刻说"注释没更新，实现已经筛场景了，就是下面这段"。
- **`jobStore.update` 没有并发保护**（无版本号、无 CAS）：Phase3 有 3 个并发任务同时写同一个 job 的 `scenesStatus` 数组，写同一字段时会丢。**如果面试官追问"并发写状态会不会有问题"，要主动承认这个**，别等被挖出来。
- **取消（cancel）不真正中断 LLM 请求**：主链路调 Phase3 时 `abortSignal` 传的是 `undefined`，所以取消只是重置状态，正在跑的请求会继续并把状态改回去。**如果你写"支持取消"，必须说清这层**："取消是状态重置，没有中断在途请求。"

## 条目 4 · 中文文本处理的几个具体问题

> 输入是网文，实际数据比预想的脏，逐个处理：
>
> **编码**：Windows 用户存的 GBK 文件按 UTF-8 读是乱码。上传时先按 UTF-8 严格模式解码，抛错就回退 GBK；解完还检出替换字符 `�` 或空字符就报错让用户重存，而不是把乱码喂给模型。
>
> **章节识别**：章节标记写法不统一（`序：` / `序章：` / `第一章` / `第1章` / `第一节` / `Chapter 1` 等 6 类），我按优先级顺序匹配并处理"两个匹配点相隔 10 字符内"的重叠去重；一条都匹配不上时按 ~2000 字回退切分，避免整本被当成一章。
>
> **角色去重**：LLM 会把同一个人的全名、别名、昵称抽成多条。我先做标点归一化，再用"短名 ≥2 字且被长名包含"判定（这条必须放在编辑距离前面，否则"林黛玉"和"林黛"这种差 1 个字的反而判不出来），最后才用 Levenshtein 距离除以较长串长 < 0.3 兜底。
>
> **时间字段**：LLM 会自创时间值。我把字段限定在 7 个枚举内，配 17 条中英表述到枚举的映射表，映射不到的落 `unknown` 而不是原样写进产物。
>
> **噪声行**：网文正文里混着盗版站水印、广告、章尾引导语、乱码行。清洗规则的设计约束是**每条规则至少要两个信号**（关键词 + 行长 ≤ 60 字，或乱码字符占比 > 0.6 + 行长 ≥ 4 字），因为单信号会误删正文——广告词偶尔出现在正常对话里，但正常对话不会只有 60 字以内。清洗结果带留痕：移除了多少行、按哪条规则、抽样原文，都记在任务的预处理报告里。

**【可追问点】**
- "为什么'包含关系'要放在编辑距离前面？" → 这是最能体现你真的写过的地方。答：中文姓名短，纯编辑距离阈值在 2–4 字的名字上非常敏感，差一个字的比例就可能超过 0.3；包含关系是给"简称/全称"这类确定性情况开的口子。
- "清洗为什么要求两个信号？" → 答：单靠关键词会误删正文（"求订阅"可能出现在正文对白里），加行长门是因为广告行几乎都很短。**并且要能说清留痕机制**——用户质疑删多了能查。

**【风险项】**
- **时间映射是 17 条，不是旧简历写的 18 条**。
- **章节正则是 7 条，但第 7 条是 Markdown 代码围栏 `/^\s*\`\`\`/gm`，不是章节标记**。被要求"说说是哪 7 种"时，要主动说明"6 种是章节标记，第 7 条是代码围栏分隔，用来处理从 Markdown 导入的情况"。
- "~2000 字"和"60 字 / 0.6 占比"都是代码常量。被问依据要答"拍的阈值，没有做误删率统计"。
- **别写"自研中文 NLP"之类的话**。这里做的是字符串处理和映射表。

## 条目 5 · 可嵌入的 Agent 工作台与 postMessage 桥

> 需求是让 Agent 工作台能被嵌到别的页面里用，但面板和宿主的业务边界是冲突的：面板如果要自己发请求，就得拿到宿主的 Cookie 和会话；宿主也不愿意把会话暴露给一个嵌进来的面板。
>
> 我把它拆成宿主和面板两侧。面板做成 web component（React 挂进 shadow DOM），**自己不持有 `fetch`、`EventSource`、Cookie 和路由**，只通过 `postMessage` 向宿主上报"意图"（启动任务 / 人工介入 / 带建议重生成 / 导航）；宿主执行真实调用、订阅 SSE，再把 Agent 事件回推给面板渲染。协议消息统一带协议版本 `_v` 和请求关联 ID `refId`。
>
> 宿主侧做了两层入站守卫：origin 白名单 + 消息结构校验（缺版本号、缺类型、类型不在白名单的一律拒绝），伪造 origin 的消息在进入业务 handler 之前就被丢掉了。配了两个宿主 demo（同页 web 宿主 + 跨域 iframe 宿主）和协议单测，覆盖 schema 校验、白名单放行、伪造 origin 拒绝、事件往返。

**【可追问点】**
- "为什么要 shadow DOM？" → 答：面板会被嵌进别人的页面，样式必须和宿主隔离，否则宿主的全局 CSS 会污染面板，反之亦然。
- "有了 origin 白名单为什么还要校验消息结构？" → 答：origin 只能证明消息来自哪个窗口，不能证明内容合法；同一个 origin 上可能有别的脚本或旧版本面板。两层缺一不可。

**【风险项】**
- **白名单目前是硬编码的 4 个 localhost 地址**（`localhost:3004` / `127.0.0.1:3004` / `localhost:3003` / `127.0.0.1:3003`）。被问"生产环境怎么配"要主动说："现在是硬编码的 dev origin，生产要改成配置注入或按租户下发，这块还没做。"
- **不要写"微前端框架/方案"**。这是一个单组件的嵌入式桥协议，不是微前端体系。
- **Tauri / Electron 桌面壳只写了一份后续规划文档，没有实现**。别写"支持桌面端"。
- **不要写"长列表虚拟化"或"SSE 节流"**——全仓搜不到任何虚拟化或节流实现（见 R-04）。如果确实需要讲性能，只能讲真实的：面板只渲染事件流驱动的有限状态，不持有全量任务数据。
- 单测是协议层单测（81 行），**没有覆盖两个宿主 demo 的端到端行为**。别把它说成"完整的集成测试"。

## 条目 6 · 【挂起 · 建议先自证再决定写不写】Agent 运行时与四阶段编排

这条我**单独挂起**，因为它最危险。先看事实：

**可以安全主张的部分**（有代码、有测试）：
- 实现了一个 Agent 运行时：7 个状态的状态机 + 转移表驱动、三层记忆（工作记忆超预算时淘汰最旧消息 / 会话记忆保留最近 20 轮 / 长期记忆持久化）、事件发射、步数与 token 预算上限、取消。
- 用这个运行时把四阶段转换做成了"每阶段一个 Agent 实例"的串行编排，每阶段结束过一道质量门（5 道门的分数阈值、必查维度、最大问题数、失败动作、最大重试次数都是配置表），支持门不通过时挂起等人工介入（4 种动作：通过 / 重试 / 带建议重做 / 丢弃），任务持久化后可重启续跑。
- 门的判定顺序是有设计的：身份一致性失败优先否决 → 逐个必查维度与阈值比 → 问题数超限 → 总分不达标 → 总分落在阈值以上 10 分区间内判"建议人工审核"。

**必须主动说明的边界**（否则一追就崩）：
- **工具调用没有接通**。`LLMChatOptions` 里根本没有 `tools` 字段，Agent 的 LLM 适配层只转发了 `temperature/maxTokens/signal`，从内容里解析工具调用的那个函数从头到尾没有被调用过。结果是：工具调用列表恒为空，`executeTool` 永远不会被触发，**仓库里那 8 个内置工具（启动管线、查状态、取消、抽角色、抽地点、合并校验、存历史、取结果）在实际编排链路里一次都不会被调用**，每个阶段就是"调一次 LLM 然后结束"。
- 身份一致性重转链默认关闭，且它依赖一个从不被填充的 `identity` 字段，所以那整条链在默认配置下不可达。
- Agent 注册表从未被初始化，任何 Agent 间交接都会返回"没有可用的实例"。

**【可追问点】**
- "Agent 怎么决定调用哪个工具？" → **这是必被问的，也是你现在答不了的**。除非你先自己把工具链路接通并跑通。
- "每阶段一个 Agent 实例，和直接顺序调用有什么本质区别？" → 能答的部分：状态机 + 记忆淘汰 + 预算上限 + 事件流可被 SSE 消费 + 阶段产物可落库和恢复。

**【风险项】**
- **强烈建议**：要么先花半天把工具调用接通（给 `LLMChatOptions` 加 `tools`、在适配层转发、调 `extractToolCallsFromContent`），要么**这条不要写进简历**。
- 如果你决定写，措辞必须停在"实现了 Agent 运行时骨架（状态机/记忆/预算/事件）并复用它做四阶段编排"，**并且主动交代"工具调用链路未接通，当前每阶段是一次 LLM 调用"**。主动承认比被挖出来强得多——但坦白之后，这条在"Agent 能力"上的说服力就有限了，你要判断它值不值得占简历篇幅。

# 【3】面试复习资料

## 第一层：必须能答

针对上面 5 条（+1 条挂起）的必答题。**答案要点全部基于代码事实，不要在这之上加料。**

### 对应条目 1（容错解析）

**Q1：`safeJsonParse` 的四层降级具体是什么顺序，为什么是这个顺序？**
要点：① 直接 `JSON.parse`（最快，命中率最高）② 剥掉 ` ```json ` 围栏再 parse ③ 括号配对扫描：从第一个 `{` 或 `[` 开始做深度计数，深度归零处截断再 parse（处理前后有解释性文字的情况）④ 正则清理：去尾随逗号、给裸键名加引号、单引号转双引号、去控制字符。顺序 = 成本顺序，前三层覆盖绝大多数情况，第四层是兜底。
边界：说清第四层是"补救"不是"常态"；我没统计过各层命中率。

**Q2：为什么解析失败要返回哨兵而不是抛异常？代价是什么？**
要点：解析器被多处复用（Phase1/2/3、场景重写），抛异常会强制所有调用方写 try/catch。哨兵把"是否重试"的决定权留给调用方。
代价（**这是加分点，主动说**）：漏检哨兵会把解析失败当成合法的空结果，重试永远不触发。我在 Phase1 就踩过这个坑——大长篇会静默丢角色卡。修法是在 Phase1 调用点显式检查 `_parseError` 并抛错。

**Q3：怎么判断 LLM 输出被截断了？**
要点：只看"内容数组恰好只有 1 个块，且这个块的 `description + line` 长度超过 3000 字"这一种形态。设计上是高精度低召回——缺 `content` 字段或空内容都是合法响应（确实没东西可转），不能报截断；误报会浪费一次重试的 token。

### 对应条目 2（长文本上下文）

**Q4：整本书装不进上下文，你的方案是什么？**
要点：三条路径。① 基线：按比例截断到 3 万 token 单次分析。② map-reduce：按章并行抽取实体/摘要/伏笔，再归并成全局设定卡，归并由 LLM 做分组决策，每个实体记 `mergeProvenance`（这个称呼来自哪一章）以便回溯。③ 长上下文：整本不截断送大窗口模型，前置守卫检查估算 token 是否超过模型窗口的 90%。
三条都保留，切换靠 `resolvePhase1Mode`，优先级是显式参数 > 环境变量 > 默认单点。
边界：**默认是截断基线**，因为我没有做出能证明另外两条更优的对照数据。

**Q5：reduce 阶段怎么把跨章的同一个人合并？规则还是模型？**
要点：合并决策交给 LLM（输出归并分组），因为"同人不同称呼"需要语义判断。规则只做**归并前的冲突预警**，三类信号：别名被多个候选共用或撞他者主名、循环别名、同名候选跨章 ≥30 章且各自标签非空但无交集。纪律是**只预警不裁决**——不做自动合并或拆分，避免把模型的不确定性换成规则的武断。

**Q6：Phase3 的上下文怎么控制体积？**
要点：主角卡常驻注入所有场景（主角数量少）；配角只注入本场景在场名单里命中的；前 5 章的滚动摘要；按章节区间筛未闭合的伏笔。三者皆空时回退全量，防止上下文为空。裁剪量会打日志，`charsKept/charTotal` 可观测。

### 对应条目 3（持久化与恢复）

**Q7：任务状态为什么从内存搬到数据库？**
要点：内存方案靠 `globalThis` 挂载躲 Next.js 热重载引起的模块重执行。但重启就丢、多实例不共享、用户没有任何补救路径。
做法：保留原来的类和方法签名做兼容壳，内部转调 repository，调用点一行不改——这是为了控制改动面，不是为了"设计优雅"。

**Q8：恢复锁怎么实现的？为什么不用 Redis？**
要点：一条 `UPDATE jobs SET lock_owner=?, locked_at=? WHERE id=? AND (lock_owner IS NULL OR locked_at < ?)`，`changes > 0` 即抢到锁。CAS 语义靠 WHERE 条件表达，不需要事务。TTL 10 分钟，长恢复按 TTL/3 心跳续锁。
为什么不用 Redis：单库场景够用，省一个外部依赖。
**主动说边界**：这是单库 CAS，不是分布式共识；分库场景不适用。TTL 10 分钟是拍的，没有按恢复耗时统计过。

**Q9：恢复是重跑全量还是只重跑失败场景？**
要点：现在只挑 failed/pending 的场景重跑 Phase3，再按 `sceneNumber` 与旧产物对齐合并，最后重跑 Phase4 重合并。
能对齐的前提是 Phase2 不重跑，所以场景号稳定。
**主动提**：代码注释里还留着 `TODO: 重跑全量`，那是没更新的注释。

**Q10：你修过的印象最深的一个 bug？**
要点：重转路径的状态覆盖。Phase3 的 `convertScenes` 一进来就无条件把任务状态写成 `converting`，而设定卡编辑这种"局部重转"的收尾代码没有写回终态，导致任务永远停在"转换中"。是集成测试抓到的，修法是在重转收尾显式写回 `completed`。

### 对应条目 4（中文处理）

**Q11：中文姓名去重为什么用"包含关系 + 编辑距离"而不是只用其中一个？**
要点：中文姓名短（2–4 字），纯编辑距离对短串极其敏感——"林黛玉"和"林黛"归一化后距离 1，除以长度 3 得 0.33，超过 0.3 阈值就被判为不同人。所以先用"短名 ≥2 字且被长名包含"这个确定性规则捞一遍（处理简称/全称），再用编辑距离兜底（处理错别字、音近字）。

**Q12：噪声行清洗怎么避免误删正文？**
要点：设计约束是**每条规则至少两个信号**：关键词匹配 + 行长 ≤60 字，或者乱码字符占比 >0.6 + 行长 ≥4 字。加行长门是因为广告行几乎都很短，而正常正文即便含"求订阅"这类词也不会短。唯一例外是 URL/域名规则（单信号），因为它特征足够特异。
另外清洗**只删整行不改行内**，并留痕（移除行数、按规则分类计数、抽样原文截断 60 字）。

**Q13：编码问题怎么处理的？**
要点：`TextDecoder('utf-8', { fatal: true })` 先严格解码，抛错就 `iconv` 回退 GBK；解完检出替换字符 `�` 或空字符就返回 400 让用户重存，而不是把乱码喂给模型。上传前把 CRLF/CR 统一成 LF。

### 对应条目 5（可嵌入工作台）

**Q14：面板和宿主的职责怎么切的？为什么这么切？**
要点：面板**不持有** `fetch` / `EventSource` / Cookie / 路由导航，只上报意图（start / review / revise / navigate）；宿主执行真实调用 + 订阅 SSE，把 Agent 事件回推给面板渲染。
为什么：面板要自己发请求就必须拿到宿主的会话，这在跨域 iframe 场景下既做不到也不该做；切完之后换宿主只需重写宿主侧适配，面板不变。

**Q15：桥的安全模型是什么？**
要点：两层——origin 白名单（四个 localhost dev origin）挡掉非预期窗口，消息结构校验（必须有 `_v` 版本号、`type` 在白名单内、必须有 `refId`）挡掉同 origin 上的非法内容。伪造 origin 的消息在进入业务 handler 前就被丢弃，有单测覆盖。
边界：白名单现在是硬编码，生产要改成配置注入或按租户下发，没做。

## 高频追问 TOP5

### TOP 1：这个项目里最难的技术问题是什么，你怎么解决的？

**答题思路**：不要答"LLM 输出不稳定"这种泛泛的。挑一个**有具体现象 + 有定位过程 + 有修法**的。推荐讲**指标累加的静默失效**：

> 我给管线加了运行期指标（token 消耗、预算拦截次数、角色名占位率），落库后发现 token 数是对的，但"调用次数"永远是 1、"预算拦截"永远是 1、"占位率"从不累加。
> 定位过程：指标写在一处"读旧值再累加"的代码里，看起来没问题。真正的原因是任务更新方法每次都会从数据库重新加载整行，而指标原先存放的那个字段**根本没有持久化路径**——所以每次"读旧值"读到的都是空，累加永远从零开始。
> 修法：把累加搬到运行期的累加器对象上，在阶段边界随产物一起落库；同时保留旧字段的读取兼容。另外加了防御式归一化，从任意 JSON 恢复指标时未知或损坏的值一律归零，并且能标记"指标不完整"（比如从旧任务恢复后只统计了恢复之后的部分）。

**诚实边界**：可以答的是现象、定位过程、修法、以及"这个修法是先写集成测试发现不对才定位的"。**不要答**"我做了完整的指标监控体系"——你只有 usage / 预算拦截 / 占位率 / 阶段耗时这四类，且没有可视化大盘（调试页只是把聚合数字列出来）。

### TOP 2：为什么不用现成的方案？比如队列、ORM、Agent 框架？

**答题思路**：这题考的是**取舍意识**，不是选型清单。逐项答：

> - **任务队列**：项目里有一个遗留的内存队列实现，我把它删掉了，只保留"引擎 + 任务存储"这一条执行路径。理由是有两条路径就会有状态不一致，而这个项目的任务本来就是要落库的，队列是多余的中间层。
> - **ORM**：存储层只用 `prepare().run/get/all` 三个方法，仓储代码本身就很短。引入 ORM 的收益（类型安全的查询构造）在这里不明显，代价是学习成本和一层不可控的生成 SQL。
> - **Agent 框架**：这里我要坦白——我确实自己写了一套 Agent 运行时，但工具调用链路没有接通，所以它现在的实际效果等同于"每个阶段调一次 LLM 的状态机"。如果重做，我会先验证框架（LangGraph 之类）能不能满足"阶段产物落库 + 挂起等人工介入 + 重启续跑"这三个硬需求，再决定要不要自己写。

**诚实边界**：**这一段最忌讳硬撑**。"我评估过现成框架、结论是不合适"这种话如果没有真实评估过程，会被追问"你评估了哪几个、各自的扣分点是什么"。推荐口径是承认"没做正式选型，是按当时的需求直接写的"。

### TOP 3：这套东西怎么保证输出质量？你怎么知道它变好了？

**答题思路**：这题是**陷阱题**——因为正确答案是"我没有数据，只有机制"。如实说：

> 我搭了三层机制，但老实说**第二层的结论数据我还没跑出来**。
> - **确定性规则**：三条身份断言——死去的角色不能在其死亡章之后说话、真名未揭示前不能用真名、别名不能直接当 characterId。这三条不需要 LLM 就能判定，而且设计上会跳过"无法判定"的场景（比如没有章节归属信息的），所以在人工标注还不完整时不产生假阳性，成本是零。
> - **LLM 评分 + 基准集**：8 个手工样本，4 个是分档标尺（优秀/良好/合格/差），4 个是定向缺陷样本（一致性差/连贯性差/戏剧性差/格式差）。核心断言不是绝对分数，而是**判别力**：好样本的得分必须高于差样本。绝对档位允许 ±1 档，避免过严。
> - **稳定性分析**：同提示词重复采样分析方差，用噪声带决定阈值。
> 瓶颈在于：分层对比的数据还没跑出来，所以我现在只能讲机制，不能讲"质量提升了多少"。

**诚实边界**：可以答机制细节（三条规则、8 个样本的构成、判别力断言）。**必须主动承认**曲线数据未出。**绝对不能答**"质量通过了验收/提升明显"——你自己的文档里就写着"不写曲线判定通过"。

### TOP 4：你的并发和限流是怎么设计的？

**答题思路**：这题是**送分题也是丢分题**。设计本身简单，关键是把"为什么这么定"讲清楚并且**不吹**：

> 场景转换是并行做的，用一个信号量把并发限制在 3；另外配了一个令牌桶限流（容量 50、每分钟补充），在每次调用前 `wait`。
> 为什么是 3：保守取值，因为并发上去之后内存开销线性增长，而且对上游 API 的 429 风险变大。这个值是拍的，**没有做过压测或不同取值的对比**。
> 限流这块我要说明：当前 3 并发的情况下，一分钟内基本打不满 50 次，所以令牌桶实际上几乎不会被触发——它的定位是"未来把并发调高时的上限保护"，不是现在在起作用。我没有观察到过触发记录。
> 错误处理上用的是 `allSettled`，单个场景失败不阻塞其他场景；失败场景降级为一条带错误码的占位内容 + `confidence 0.1`，任务整体不失败。

**诚实边界**：可以答设计意图和数值来源（代码常量）。**不要答**"经过压测调到 3"或"限流保证了稳定性"。HOLD 不住的地方是"3 是不是最优"——直接承认没比较过。

### TOP 5：如果让你重做，你会改什么？

**答题思路**：这题考的是**自我认知**。给三个有说服力的答案，全部来自你代码里的真实缺陷：

> 1. **先接通 Agent 的工具调用再写编排**。现在的问题是我把编排、门禁、持久化、记忆都写完了，但工具调用这一环没接通——`LLMChatOptions` 里没有 `tools` 字段，解析工具调用的函数从来没被调用过。结果是那 8 个内置工具在编排链路里一次都不会执行，每个阶段就是一次 LLM 调用。这些东西应该先用一个最小的端到端链路验证再往上堆。
> 2. **给任务更新加并发保护**。任务更新方法每次从库里读最新状态再写回，但没有版本号或 CAS，所以并发写同一个字段（比如场景状态数组）会丢写入。Phase3 有 3 个并发任务写同一个任务，这是真实存在的竞争。修法可以是版本号乐观锁，或者把数组字段改成追加式的。
> 3. **取消要真的中断请求**。目前取消只是把状态重置，主链路给 Phase3 传的取消信号是 `undefined`，所以正在跑的请求会继续，并在完成时把状态改回去。应该把取消信号从路由层一路传到 LLM 调用。

**诚实边界**：这三个都是可验证的真实缺陷，答出来**加分**——它证明你读过自己的代码并且知道问题在哪。**不要**答"重做会引入微服务/K8s/消息队列"这类与项目规模不匹配的答案。
