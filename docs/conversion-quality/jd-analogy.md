# 同构类比：小说→剧本与代码工程

> 目的：面向 Coding Agent 类 JD 面试，把本项目「长篇小说→剧本」的转换质量工程，映射到求职者熟悉的代码工程词汇，形成**一句话口径**："域不同，工程问题相同"。
> 日期：2026-08-29 ｜ 关联：`docs/conversion-quality/jd-coverage.md`、conversion-quality spec。

## 一句话口径

> 我把一部几十万字的长篇小说当成一个**大型代码仓库**来管理上下文：超长输入靠**分模块摘要（map-reduce）**压进上下文、重复出现的实体靠**代码索引**按需注入、转换质量靠**测试断言**做可复现验证。域是"小说→剧本"，落的是和做 Code Agent 一模一样的工程问题：**大上下文下的信息不丢失、实体不混乱、效果可度量**。

## 边界（诚实标注，不假装）

- **域不同**：另一端是"剧本结构"而非"可运行代码"；产出不参与编译 / 运行 / 测试闭环。
- **JD#4 代码工具（Git/终端/文件修改/P4）在转换域没有对应物**：角色/场景不是文件，`sort`/`grep`/`git diff` 这类代码工具链不适用。管道形态同构，但真正操作代码仓库的 Agent 工具是空档——这一点在 `jd-coverage.md` 如实标注。

## 为什么这组类比成立（不靠话术）

它们不是隐喻层面的相似，而是**同一种工程约束的解**：
- 上下文窗口有限 → 都是"先粗消化、再按需取细节"（map-reduce ↔ 分模块摘要）。
- 标识重复出现 → 都要"一次定义、处处引用"并防命名漂移（别名索引 ↔ 符号表）。
- 效果不可靠 → 都要"最小断言 + 方差分析"而非"目测变好了"（身份断言 ↔ 测试 / Δ_tail ↔ benchmark 噪声）。

所以这套能力在换到 Coding Agent 域时，改的是**域对象**（repo/文件/符号），不改的是**方法**（摘要/索引/断言/门禁/预算）。
