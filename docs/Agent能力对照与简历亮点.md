## 第 0 部分：结论先行

**这个项目在 Agent 全栈上的真实位置是：「框架层基本齐、能力层差 3 处代码、域工具是空档」。**

| 层次 | 状态 | 说明 |
|---|---|---|
| **框架层**（编排、状态、恢复、HITL、上下文、记忆、观测、网关、嵌入、前端） | ✅ 大部分可讲 | 其中**上下文管理是真正的核心资产**，直接命中 JD#3，论证力最强 |
| **能力层**（工具调用闭环：模型能自己决定调什么工具、拿到结果继续推理） | ◐ 差 3 处代码 | 工具注册表、8 个内置工具、执行器、日志包装、响应解析**全都写好了**，唯独「把工具定义发给模型」这一步没做，导致整条链不触发。**约半天可接通** |
| **域工具层**（代码域：Git / 终端 / 文件读写 / P4） | ✗ 空档 | JD#4 要求的四种代码工具在本项目没有对应物。你自己的 `jd-coverage.md` 已如实标注 |

**所以「Agent 全栈」的正确论证姿势是**：证明我**把 Agent 的每一层都亲手实现过一遍**（而不是用了某个框架跑通 demo），并且我清楚 JD#4 的代码域工具是本项目域对象（小说→剧本）决定的结构性空档——**框架我全做了，域工具我缺一类**。这个位置是能站住的，前提是**不要主张"Agent 能自主调工具完成转换"**——那一步没通。

## 第 2 部分：逐组件展开

### 1. Agent 循环与编排 ✅

**是什么**：Agent 的心跳——读上下文 → 让模型决策 → 执行动作 → 观察结果 → 循环，直到终态或触顶。

**本项目证据**：`lib/agent/AgentCore.ts`（470 行）。手写 ReAct 循环，7 个状态（idle/planning/executing/reasoning/awaiting/done/error），转移合法性由**表格驱动**的 `state-machine.ts` 单独维护（`TRANSITIONS` 数组是唯一真理源，拍平成 `Map<state, Set<next>>` 做 O(1) 判定）。循环里有两道上限：步数（编排器传 20）与 token 预算（64000），触顶即置错误态退出。取消走 `AbortController`。编排层 `MultiAgentOrchestrator` 把四阶段做成一阶段一个 AgentCore 实例，串行推进，每阶段产物落库。

**为什么算 ✅**：状态机、循环、上限、取消、事件发射都有代码，`AgentCore.events.test.ts` 有测试。

**要主动交代**：主循环里状态转移是**直接赋值**而不是走校验函数（校验函数只在两处被调用），所以状态机的"表"是文档+局部校验，不是全局强制。另有两个已确认缺陷：`state_change` 事件里的 `from` 恒为 `planning`（赋值顺序错），`resume(userInput)` 的输入会被 `run()` 开头的记忆重置清掉。

**简历怎么写**：
> 实现 Agent 运行时：7 状态状态机（转移表驱动）+ 手写 ReAct 循环，配步数与 token 预算双上限、可取消的事件发射；用其把四阶段转换做成一阶段一实例的串行编排，阶段产物全部落库。

**会被问**：「为什么自己写不用框架？」→ 见第 3 部分口径，**不要硬撑"评估过现成框架"**。

### 2. 工具系统 ◐ —— **这是你现在最该动的地方**

**是什么**：Agent 的手脚。工具 schema 定义 → 注册 → 把定义发给模型 → 解析模型返回的工具调用 → 分发执行 → 把结果回灌。

**本项目证据（写好的部分）**：
- `lib/tools/tool-registry.ts`：`ToolDefinition {id, name, description, inputSchema, category, tags, estimatedDuration, estimatedTokens, enabled, handler}`，6 个分类（pipeline/analysis/conversion/validation/storage/utility），支持按分类列出与按名称/描述/标签搜索，`execute` 永不抛错（统一转 `{success, error, durationMs}`）。
- `lib/tools/builtin-tools.ts`：8 个工具——`start_pipeline` / `get_pipeline_status` / `cancel_pipeline` / `extract_characters` / `extract_locations` / `merge_validate` / `save_to_history` / `get_result`，每个都带**完整 JSON Schema**（`{type:'object', properties:{...}, required:[...]}`）。
- `lib/tools/builtin-tools-assembly.ts`：业务侧依赖注入装配（`startPipeline` 接 `PipelineEngine.startJob`、`analyzeText` 接 Phase1 分析器、`merge` 接 Phase4 合并器）——**这是解耦做得对的地方**：`builtin-tools.ts` 不 import 任何 pipeline 模块。
- `lib/agent/debug/logging-tool-executor.ts`：工具调用日志包装。

**为什么是 ◐（缺的那一步）**：
这条链有 5 跳，**前 4 跳都是通的，断在第 5 跳**：

```
AgentCore.callLLM()                       传 config.tools          ✓
  → AgentCoreLLMAdapter.chat(messages, tools)  调 inner.setTools(tools) ✓
    → AgentLLMProvider.setTools(tools)         存进 this.tools        ✓
      → AgentLLMProvider.chat(...)             根本不读 this.tools    ✗ ← 断在这里
        → 底层 provider.chat(options)          选项里也没有 tools     ✗
```

`lib/llm/types.ts` 的 `LLMChatOptions` **只有** `temperature / maxTokens / responseFormat / signal`——**没有 `tools` 字段**。所以模型**从来不知道有哪些工具**，自然不会返回工具调用；`parseLLMResponse` 只能读 OpenAI 原生的 `message.tool_calls`，读到空；`AgentCore` 的工具分支永不进入，8 个内置工具在编排链路里一次都不执行——**每个阶段实际是一次 LLM 调用**。

**一个有利的发现**：`DeepSeekProvider` / `OpenAIProvider` / `CustomOpenAIProvider` 都**已经回填了 `raw: json`**，而 `parseLLMResponse` 正是从 `raw.choices[0].message.tool_calls` 读的。所以**响应侧一行都不用改**——只要把工具定义发出去，原生 `tool_calls` 就能被解析。整条链只差"发出去"这一跳，外加修 schema 转换。

附带的两个问题：① `toOpenAITool` 把**整个 JSON Schema 对象**当参数表遍历（应该读 `.properties`），即使发出去也是错的定义 ② `ROLE_TOOLS` 声明的工具名与真实工具名大部分对不上（analyzer 的 4 个里有 2 个对得上，其余 4 个角色全部对不上），且这个常量**没有任何消费方** ③ `createToolExecutor` 把 `taskId` / `agentRole` 硬编码成 `'unknown'`，工具无法与任务关联。

**简历怎么写**：**先接通，再写。** 接通后可以写：
> 实现工具注册表（JSON Schema 定义、分类与标签检索、启用位、统一执行与日志包装）与 8 个内置工具，覆盖管线启停/状态查询/实体抽取/合并校验/结果存取；工具依赖由业务侧注入装配，工具模块不依赖编排模块。

**会被问**：「演示一下 Agent 自己调工具」「工具调用的结果怎么回灌给模型？」「工具执行失败了模型怎么知道？」——**这三个问题现在都答不了。**

### 3. 模型网关与多 Provider ✅

**是什么**：Agent 的模型出口，以及对多模型/多来源的统一收口。

**本项目证据**：`lib/llm/` 24 个文件。`BaseProvider` 承载共享 HTTP 逻辑（30s 超时、2 次重试、组合 AbortSignal 把外部取消与内部超时合并、流式 SSE 解析、tiktoken 估算懒加载）；4 个实现：DeepSeek、OpenAI、自建 OpenAI 兼容、Anthropic 原生（覆写鉴权头为 `x-api-key` + 版本头、system 提到顶层、流式兼容两种 delta 格式、**不发 `response_format`** 因为 Anthropic 没有 JSON mode）。`llm-gateway.ts` 做按用户解析：用户导入的模型优先，未命中回退环境变量注册表，且当前调用需要严格 JSON 而用户模型不支持时会**回退到 JSON-capable provider**。`budget-controller.ts` 把 token 折算成美元做三档（分/时/月）预算守卫，`rate-limiter.ts` 是令牌桶。

**要主动交代**：`adapter/routing-strategy.ts` 实现了 7 种路由策略（含故障转移）**但零调用点**——`selectAdapter()` 在整个仓库里没人用；`ModelRouter` 实际用的是"最低 currentLoad"，而那个 `currentLoad` 是**累计请求计数且从不递减**（10 次请求后永久饱和），语义上不是并发度。`MODEL_COSTS` 表在两个文件里重复且字段名不同。**所以"路由/故障转移/负载均衡"这些词一个都不能写。**

**简历怎么写**：
> 实现 LLM 接入层：统一的 Provider 抽象（超时/重试/取消信号合并/流式解析）+ 4 个实现（含 Anthropic 原生协议的鉴权与流式差异处理）；支持用户导入自定义模型（OpenAI 兼容与 Anthropic 两种协议）并按用户解析优先级，用户模型不支持 JSON 模式时回退到支持的模型；配美元三档预算守卫与令牌桶限流。

**会被问**：「Anthropic 和 OpenAI 协议的差异你怎么处理的？」（送分，答鉴权头、system 位置、无 JSON mode、delta 字段名）「网关的降级会不会让用户以为在用自己配的模型？」（**诚实答：会，且没有对用户提示，这是待改的点**）

### 4. 上下文管理与长文本 ✅✅ —— **主推这条**

**是什么**：Agent 最核心的能力——在有限窗口里装下超长输入，并且**在需要的时候把该有的信息取回来**。

**本项目证据（这是真做扎实的部分）**：
- **不做截断的三条路径**：① 基线：按比例截断到 3 万 token 单次分析 ② **按章 map-reduce**：每章并行抽取实体/时间线/章节摘要/开放伏笔 → 再跑一次归并（归并决策交 LLM，每个实体记 `mergeProvenance` 记录"这个称呼来自哪一章"以便回溯）③ **整本长上下文**：不截断送大窗口模型，前置守卫检查是否越过窗口 90%。三条路径由**单一决策函数**切换（显式参数 > 环境变量 > 默认），默认不切。
- **超长单章二次分块**：超过阈值按 token 分块后逐块抽取再合并该章结果。
- **设定卡（ContextCard）**：章节摘要 + 未闭合伏笔池（`openThreads` 带起止章），这是"先粗消化、再按需取细节"的落点。
- **场景级上下文装配**：主角卡常驻注入所有场景 + 配角只注入本场景在场名单命中的 + 前 5 章滚动摘要 + 按章节区间筛未闭合伏笔；三者皆空时回退全量防止上下文为空；裁剪量打日志可观测。
- **按章取卡**：`resolveCardView(char, chapterIndex)` 支持角色的**分阶段卡**（某章之后性格/状态变了的角色卡切换），另有真名揭示章控制（`revealAt` 之前的章节只能用别名口径）。
- **预算守卫接到调用点**：每章/每次调用前估算 token 并查预算，超限**优雅降级跳过**而不是崩管线。

**为什么是 ✅✅**：这是唯一一块"机制完整 + 有明确设计取舍 + 有确定性单测"的部分。而且它**直接命中 JD#3 的第一条**。

**类比口径**（你自己已经有了，`jd-analogy.md`）：把几十万字长篇小说当成一个大型代码仓库来管上下文——map-reduce ↔ 分模块摘要/增量索引，设定卡 ↔ 代码索引/符号表，在场角色名→实体ID 的解析 ↔ 符号解析，身份断言 ↔ 测试断言。**域不同，工程问题相同。**

**简历怎么写**：
> **长文本的上下文管理**：整本小说几十万字装不进上下文，原方案截断到 3 万 token 后单次分析，截断位置落在句中且后半本书的实体不参与分析。新增按章并行抽取→全局设定卡归并（每个实体记录称呼出处以便回溯）与整本不截断的长上下文两条路径，三条路径保留、切换由独立决策函数负责（数据不足不切默认）；场景上下文改为"主角卡常驻 + 配角按在场名单注入 + 前 5 章滚动摘要 + 未闭合伏笔按章节区间注入"，prompt 体积与全书角色数解耦；调用前估算 token 并过预算守卫，超限降级跳过而非中断任务。

**会被问**：「归并怎么判断同一个人？」「为什么默认不切 map-reduce？」「角色卡按章切换解决了什么问题？」——三个都能答，且答得漂亮。

### 5. 记忆 ◐

**是什么**：Agent 跨步、跨轮、跨会话的信息保留与淘汰。

**本项目证据**：`lib/agent/memory.ts`（335 行）三层——**工作记忆**（每任务，超过 70% token 预算时丢弃最旧消息，每次调 LLM 前先淘汰）、**会话记忆**（保留最近 20 轮 assistant+tool 消息，重注入时截断到 300/500 字）、**长期记忆**（带标签的条目标目，可增删改查与按标签过滤）。

**为什么是 ◐**：两个短板。① **长期记忆落在 `localStorage`**（key `novel2screenplay_agent_memory`）——这与项目其他地方"历史已迁到服务端 SQLite"的方向相反，换浏览器即失忆，且多设备不共享。② token 计数是**字符启发式**（0.25 token/字，代码注释自己标注为 tiktoken 占位），不是真实计数。

**简历怎么写**（要带着短板写，不要单列一条吹）：
> Agent 记忆分三层实现：工作记忆在接近 token 预算时按最旧优先淘汰、会话记忆保留最近 20 轮并做截断重注入、长期记忆条目化支持增删改与标签过滤。长期记忆当前落在浏览器本地存储，尚未与服务端统一。

### 6. 任务状态与恢复 ✅

**是什么**：Agent 长任务的 checkpoint 与 resume——进程崩了、重启了，任务不能凭空消失。

**本项目证据**：
- Agent 侧：`agent_tasks` 表存**整份任务 JSON**（`upsert ... ON CONFLICT DO UPDATE`，`created_at` 故意不在更新列里所以创建时间不会被覆盖），`loadActive()` 按 `created_at ASC` 稳定取回，`restoreFromPersistence()` 把**崩溃时停留在"运行中"的阶段重置为待处理**再续跑，而**挂起等待人工的阶段保持挂起不自动推进**。
- 主链路侧：恢复锁是数据库层**单条 `UPDATE` 达成的 CAS**（`WHERE lock_owner IS NULL OR locked_at < 过期时间`，以 `changes > 0` 判定是否抢到），带 10 分钟 TTL 与 TTL/3 心跳续锁；恢复从"重跑全量"改为只重跑失败/待处理场景后重合并。
- 还修过一个集成测试抓到的缺陷：局部重转路径进入时把状态写成"转换中"，收尾未写回终态，任务永久卡住。

**简历怎么写**：
> Agent 任务状态与恢复：任务整份落表，重启时把崩溃遗留的"运行中"阶段重置为待处理后续跑、挂起等待人工的阶段保持挂起；主链路恢复锁用数据库单条 UPDATE 实现 CAS（锁为空或已过期才可抢），配 TTL 与心跳续锁；恢复只重跑失败与待处理场景而非全量。修复一处状态覆盖缺陷（局部重转收尾未写回终态导致任务永久卡住）。

**会被问**：「为什么用一条 UPDATE 当锁？」「TTL 为什么 10 分钟？」（**后一个要答"拍的，没按恢复耗时统计过"**）「挂起态重启后会自动继续吗？」（答：不会，保持挂起等人工）

### 7. Human-in-the-loop ✅

**是什么**：Agent 跑到关键节点停下来等人拍板。

**本项目证据**：`OrchestratorPhase.status` 有独立的 `awaiting` 态；门不通过且失败动作是 `manual_review` 时 `parkAwaiting()` 挂起并 break 循环；`resolveManualReview(taskId, phaseId, action, instruction)` 支持 4 种动作——**通过**（阶段标完成，从下一阶段续跑）、**重试**（重试计数 +1，从本阶段重跑）、**带建议重做**（同重试，并把建议追加进任务的持久化指令，**该指令会影响所有后续阶段**）、**丢弃**（阶段标失败，任务终结）。有守卫：任务必须真的处在该阶段的挂起态才能处理。前端 `AgentChatPanel` 渲染阶段卡片 + 门决策文案 + 干预按钮；SSE 推 `phase_awaiting_manual`。

**简历怎么写**：
> 实现人工介入闭环：阶段级挂起态 + 四种处置动作（通过后续跑 / 重试本阶段 / 带建议重做 / 丢弃终结），干预指令持久化并影响后续阶段；前端渲染门决策并支持操作，SSE 推送挂起事件。

**会被问**：「'带建议重做'和'重试'的区别？」（答：前者会把建议写进任务的持久化指令，后续阶段也会带上，所以是"全局纠偏"；后者只是重跑）「重试次数被谁消耗？」（**诚实答：人工重试和自动重试共用同一个计数器**，这是已知的耦合）

### 8. 质量门与验证 ◐

**是什么**：Agent 的自我检查关卡。

**本项目证据**：`lib/multi-agent/review-gate.ts`。5 道门配置表（`analysis_characters` / `segmentation_scenes` / `conversion_scene` / `merge_validation` / `final_quality`），每道门有分数阈值、必查维度、问题数上限、失败动作（重试或人工）、最大重试次数。**判定顺序是有设计的**：身份一致性失败优先否决 → 逐个必查维度与阈值比 → 问题数超限 → 总分不达标 → 总分落在阈值上方 10 分区间内判"建议人工审核" → 否则通过。LLM 评估器抛错时**降级到内容启发式**（有场景标记给 85 否则 70、有对白给 80 否则 65 等），保证门本身不会崩。

**简历怎么写**（只写站得住的部分）：

### 10. 评测体系 ◐

**本项目证据**：`lib/eval/` 三块。① **确定性断言**：3 条身份规则——死去的角色不能在其死亡章之后说话、真名未揭示前不能用真名、别名不能直接当角色 ID；设计上**跳过"无法判定"的场景**，所以标注不完整时零假阳性、零 LLM 成本。② **LLM 四维评分**（格式/一致性/连贯性/戏剧性）+ **8 样本基准集**（4 个分档标尺 + 4 个定向缺陷样本），核心断言不是绝对分而是**判别力**：好样本得分必须高于差样本，绝对档位允许 ±1 档。③ **稳定性分析**（同提示词重复采样算方差、噪声带定阈值）+ **翻默认决策记录**（R1/R2/R3 规则作为常量随返回值一起返回以便审计，缺数据时返回"不裁决"）。

### 12. 流式输出 ✅

**是什么**：token 级流式，用户能看到打字机效果与中途预览。

## 第 5 部分：按 Agent 组成部分组织的简历亮点（可直接粘贴）

> 组织方式是**按 Agent 组件分组**，但每条仍写成"问题 → 解决 → 结果"，不是功能清单。
> 每条前面的括号标明它覆盖哪个组件，方便你按目标 JD 取舍、也可以把括号删掉。
> 需要评估类数字的地方一律没写数字——数据没跑出来之前不要填。

**（编排 + 状态 + 恢复）**
- Agent 任务状态与恢复：任务整份落表并按创建时间稳定取回，重启时把崩溃遗留的"运行中"阶段重置为待处理后续跑、挂起等待人工的阶段保持挂起；主链路恢复锁用数据库单条 `UPDATE` 实现 CAS（锁为空或已过期才可抢），配 TTL 与心跳续锁；恢复只重跑失败与待处理场景而非全量。期间修复一处集成测试抓到的状态覆盖缺陷（局部重转收尾未写回终态，任务会永久卡在"转换中"）。

**（编排）**
- Agent 运行时与四阶段编排：实现 7 状态状态机（转移表驱动）与手写 ReAct 循环，配步数与 token 预算双上限、可取消的事件发射；用其把四阶段转换做成一阶段一实例的串行编排，阶段产物全部落库、可重启续跑。

**（人工介入）**
- 人工介入闭环：阶段级挂起态 + 四种处置动作（通过后续跑 / 重试本阶段 / 带建议重做 / 丢弃终结），干预指令持久化并影响后续阶段；前端渲染门决策并支持操作，通过 SSE 推送挂起事件。

**（上下文管理 —— 主推）**
- 长文本的上下文管理：整本小说几十万字装不进上下文，原方案截断到 3 万 token 后单次分析，截断位置落在句中且后半本书的实体完全不参与分析。新增按章并行抽取→全局设定卡归并（每个实体记录称呼出处以便回溯）与整本不截断的长上下文两条路径，三条路径保留、切换由独立决策函数负责且数据不足时不切默认；场景上下文改为"主角卡常驻 + 配角按在场名单注入 + 前 5 章滚动摘要 + 未闭合伏笔按章节区间注入"，prompt 体积与全书角色数解耦；每次调用前估算 token 并过预算守卫，超限降级跳过而非中断任务。

**（上下文管理）**
- 按章切换的角色卡：角色在不同章节的信息量差异很大（某章之后性格/身份变了），单一角色卡会让早期章节拿到超前信息。实现按章取卡（命中区间取最晚开始的一段）+ 真名揭示章控制（揭示前的章节只能使用别名口径），未命中时回退基础卡以保持向后兼容。

**（模型网关）**
- LLM 接入层：统一 Provider 抽象（超时 / 重试 / 外部取消与内部超时信号合并 / 流式解析），4 个实现含 Anthropic 原生协议的鉴权头、system 位置与流式字段差异处理；支持用户导入自定义模型（OpenAI 兼容与 Anthropic 两种协议）并按用户优先级解析，用户模型不支持 JSON 模式时回退到支持的模型；配美元三档预算守卫与令牌桶限流。

**（可观测性）**
- Agent 可观测性：会话级事件环形缓冲 + 按任务落盘 JSONL 复盘；LLM 请求/响应与工具调用的日志包装（含失败与耗时）；五条密钥/凭证脱敏规则与长文本摘要化；提供按任务查询与清理的调试接口。

**（评测）**
- 效果评估机制：三条不需要 LLM 的确定性身份断言（角色死亡后不得发声 / 真名揭示前不得用真名 / 别名不得直接作 ID），设计上跳过无法判定的样本以避免假阳性；LLM 四维评分配 8 样本基准集，核心断言是判别力（好样本得分高于差样本）而非绝对分；另有同提示词重复采样的稳定性分析，以及"是否切换默认路径"的决策记录（缺数据时不裁决）。

**（安全护栏）**
- 安全与隔离：API Key 以 AES-256-GCM 加密落库（随机 IV + 密钥派生 + 仓储读写边界加解密 + 历史明文一次性迁移），列表接口只返回是否已配置；多租户按 `user_id` 隔离并做路由级归属校验；桥协议入站做 origin 白名单与消息结构双层守卫并配单测。

**（流式）**
- 流式输出：token 级流式供场景重写与创作辅助（NDJSON 帧 + 可中断），设计上中止时保留已收到的部分预览而不是整段丢弃；管线进度走 SSE（心跳保活、断连自动摘除客户端、前端指数退避重连并在多次失败后降级为轮询）。

**（跨端交付）**
- 可嵌入的 Agent 工作台与消息桥：把工作台拆成宿主与面板两侧——面板为 web component（React 挂 shadow DOM）且自身不持有 `fetch` / `EventSource` / Cookie / 路由，仅通过 `postMessage` 上报意图；宿主执行真实调用并订阅 SSE 后回推事件渲染。协议带版本号与请求关联 ID，入站做 origin 白名单与消息结构双层校验（伪造 origin 在进入业务逻辑前即被丢弃）。提供同页与跨域 iframe 两个宿主 demo 及协议单测。

**（前端工作台）**
- Agent 前端工作台：以事件流驱动纯函数 reducer 渲染阶段进度、质量门决策、日志与错误；处理下游 SSE 通道名有损的问题（按事件体字段判别真实事件类型）；连接断开后降级为状态轮询。

**（工具系统 —— 需先完成 P0 再启用，否则删除）**
- 工具系统：实现工具注册表（JSON Schema 定义、分类与标签检索、启用位、统一执行与日志包装）与 8 个内置工具，覆盖管线启停/状态查询/实体抽取/合并校验/结果存取；工具的业务依赖由装配层注入，工具模块不依赖编排模块。

## 附：这套论证的取舍提醒

组织方式改成"按 Agent 组件"之后，最大的风险是**又变回功能清单**——"我实现了 A、B、C"这种句子在面试里拿不到分。所以每一节我都在提示里保留了"问题是什么"。你自己再改的时候，守住两条：

1. **每条都要能答出"不做这个会怎样"**。比如状态与恢复那一条：不做的话，重启后停在"运行中"的阶段永远卡住，用户没有补救路径。答不出"不做会怎样"，说明这条是照着代码目录抄的。
2. **◐ 的那几个组件，要么接通要么不写**。面试官对"我实现了 X"的默认预期是 X 能用。工具系统和评测是最容易被追问到脸上的两个——工具系统半天能接通，评测需要一两天的对比实验，**建议优先花半天在工具系统上**。
